ラボ2 · EDU-280

内部通信のセキュア化（VLAN間トラフィックフィルタリング）

支社をオープンな状態から Zero Trust へ。デフォルトでは VLAN 間トラフィックが自由に流れることを確認し、マクロセグメンテーションルールで VLAN10 → VLAN20 をブロックし、自分のサイトだけで OT → IoT を許可するサイトレベルルールを作成します。

⚙ ラボ設定
管理者ログイン: pod##-student@<受講者FQDN> サイト名: POD##-Student-Lab ブロックルール: POD##-Block-WinServer-IoT20

ラボ2: 内部通信のセキュア化（VLAN間トラフィックフィルタリング）

マクロセグメンテーション

デフォルトでは、Zero Trust Branch デバイスは LAN/VLAN インターフェース間の通信を許可します。このラボでは、VLAN10・VLAN20・VLAN30 間のトラフィックを検証し、マクロセグメンテーション（セグメント間）を適用するファイアウォールポリシーを構成します。これは Zero Trust の東西方向制御の基礎です。

  • ping でデフォルトの VLAN 間フォワーディングを確認する
  • マクロセグメンテーションの Drop ルールで Windows Server (VLAN10) → IoT (VLAN20) をブロックする
  • サイトレベルの Accept ルールで、自分のサイトだけ OT (VLAN30) → IoT (VLAN20) を許可する
コース: EDU-280
版: 2.2 · 2026年2月
プラットフォーム: Skytap + Zscaler Experience Center
  • https://zscaler.skytap-portal.com/ に接続し、Windows Server（VLAN10）を開いて、コマンドプロンプトから他の VLAN に ping します: ping 10.1.20.10 [1] と ping 10.1.30.10 [2]。どちらも応答するはずで、デフォルトでは東西方向が開いていることが分かります。
デフォルトの動作: VLAN10 から VLAN20 (10.1.20.10) と VLAN30 (10.1.30.10) への ping が成功します。

ファイアウォールポリシーは、セグメント・アプリケーション・ユーザーグループ間のマイクロ／マクロセグメンテーションを定義し適用して、横方向の脅威の拡散を抑止します。下の図は各ポリシータイプの評価優先順位を示しています。

ポリシーの優先順位 — 各ポリシータイプが評価される順序。

2.2.1 · ブロックポリシーを構成する

  • Infrastructure › Connectors › Edge › Zero Trust Branch › Sites に移動し、POD##-Student-Lab を選択します。
自分の POD サイトを開きます。
  • Policies [1] タブを開いて Configure [2] をクリックします。ハイライトされた System-Allow-Local-Traffic-... ポリシーが、すべての VLAN 間 ping が成功していた理由です。
  • Add Policy を選択します。
Policies › Configure — デフォルトの System-Allow-Local-Traffic ルールがすべての VLAN を許可します。
Add Policy。
  • Action: Drop [1]
  • Name: POD##-Block-WinServer-IoT20 [2]
  • Source Zone: LAN_ZONE | LAN Zone [3] · Destination Zone: LAN_ZONE | LAN Zone [4]
  • Source: Network › Subnet/Host [5] › 10.1.10.0/24 [6] › Add [7]
  • Destination: Network › Subnet/Host [8] › 10.1.20.0/24 [9] › Add [10]
  • Ports: All [11] · Time Schedule Group: Mon-Fri-8-5（任意）[12]
  • Add [13] をクリックして保存します。
Drop ルール: source 10.1.10.0/24 → destination 10.1.20.0/24、全ポート。
  • Commit をクリックして適用します。コミット後、Hit Count は 0 にリセットされます。これは想定どおりで、以降のトラフィックを検証できます。
ポリシー変更をコミットします。
コミット後、Hit Count が 0 にリセットされます。
  • Skytap で Windows Server（VLAN10）を開き、10.1.20.10 に ping します。今度は 100% パケットロスで Request timed out になります。

注意: ブロックが反映されない場合、Windows が同じ ICMP ID を5分間再利用していることがあります。コマンドプロンプトを閉じて開き直す（または Ctrl+C で ping を止める）、5分待ち、その間に他のタスクを進めてから再試行してください。

Windows Server（VLAN10）を開きます。
Ping 10.1.20.10 → Request timed out、100% パケットロス。Drop ルールが機能しています。
  • ポリシーの Hit Count が 0 から 1 以上に増えたことを確認します。
Hit Count が増加 — ブロックルールがトラフィックにマッチしました。
  • 次に Skip アクションをテストします。ポリシーの歯車アイコン [1] をクリックし、Edit [2] を選択します。
  • Action を Skip [1] に変更し、Save [2] をクリックします。
  • Commit をクリックします。Hit Count は再び 0 にリセットされます。
歯車アイコン › Edit。
Action → Skip → Save。
Commit。Hit Count が 0 にリセットされます。
カスタムルールがスキップされました。
  • 再度 ping 10.1.20.10 を実行します。Skip ルールがデフォルトの許可へフォールスルーするため、今度はパケットが成功します。
  • 両方のカウンターを検証します。カスタムルールは 0 のまま（スキップ）で、デフォルトの許可ルールの Hit Count が増加します。
VLAN20 への ping が再び成功 — カスタムルールがスキップされました。
カスタムルール = 0 ヒット（スキップ）、デフォルトの東西方向許可 = ヒット増加。

シナリオ: 全社ポリシーがどこでも OT → IoT をブロックしていますが、一部のサイトでは例外が必要です。サイトレベルの Accept ルールを追加して、自分のサイトだけで OT → IoT を機能させます。

2.3.1 · まずブロックを検証する

  • グローバルポリシーがすでに 10.1.30.0/24（OT）→ 10.1.20.0/24（IoT）を全プロトコルでブロックしています。Policies › Access Control › Segmentation › Zero Trust Branch › Policies › Global Policies で確認します。
  • OT1 VM（VLAN30）から 10.1.20.10 に ping して検証します。失敗します。
グローバルポリシーが OT (10.1.30.0/24) → IoT (10.1.20.0/24) をブロック。
OT1（VLAN30）から 10.1.20.10 への ping はブロックされます。

2.3.2 · サイトレベルの Accept ルールを追加する

  • Site Policies [1] › Your-Site [2] › Configure [3] に移動します。（または Infrastructure › … › Sites › 自分のサイト › Policies。）
  • Add Policy を選択します。
Site Policies › 自分のサイト › Configure。
Add Policy。
  • Action: Accept [1]
  • Name: POD##-Allow-OT-to-IoT [2]
  • Source: Network › Subnet/Host [3] › 10.1.30.0/24 [4] › Add [5]
  • Destination: Network › Subnet/Host [6] › 10.1.20.0/24 [7] › Add [8]
  • Ports: All [9] › Add [10] をクリックして保存します。
Accept ルール: OT 10.1.30.0/24 → IoT 10.1.20.0/24、全ポート。
  • Commit をクリックします。
サイトポリシーをコミットします。
  • OT のターミナルから 10.1.20.10 に ping します。数秒以内にトラフィックが開始します。
  • ポリシーの Hit Count が 0 から増えたことを確認します。

注意: 許可が反映されない場合、Ubuntu が同じ ICMP ID を5分間再利用していることがあります。ping を止め、5分待ってから再試行してください。

OT → IoT の ping が成功 — サイトレベルの Accept がグローバルのブロックを上書きします。
サイトレベルの Accept ルールで Hit Count が増加。

完了: マクロおよびサイトレベルのセグメンテーションを検証しました。次は Policy-Based Routing を構成します。

覚えておこう
デフォルトの ZTB = 東西方向をすべて許可（System-Allow-Local-Traffic）。マクロセグメンテーション = VLAN 間（10.1.10.0/24 → 10.1.20.0/24）。アクション: Drop はブロック、Skip は次のルールへフォールスルー、Accept は許可。Hit Count はルールごとのカウンターで、変更のたびにリセットされ、どのルールがマッチしたかを示します。優先順位: サイトポリシーはグローバルを上書き — 具体的なサイトの Accept が広範なグローバルの Drop に勝ちます。ICMP-ID の5分再利用の落とし穴に注意。

ラボの進捗
クイックリファレンス ▲
マクロセグメンテーション
VLAN／ゾーン間のトラフィックを制御するファイアウォールポリシー（東西方向）。例: 10.1.10.0/24 → 10.1.20.0/24 をブロック。
System-Allow-Local-Traffic
すべての VLAN 間トラフィックを許可するデフォルトルール — ポリシー追加前に ping が成功する理由。
Action: Drop
マッチしたトラフィックをブロック（request timed out、100% ロス）。
Action: Skip
このルールをバイパスして評価を続行 — トラフィックは後続のルールへフォールスルー。
Action: Accept
マッチしたトラフィックを明示的に許可（サイトレベルの OT → IoT 許可で使用）。
Hit Count
ルールごとのマッチカウンター。変更のたびに 0 にリセット。増加 = そのルールがトラフィックにマッチ。
Commit
ステージングしたポリシー変更をデバイスに適用。ルールが有効になる前に必須。
グローバル vs サイトポリシー
サイトポリシーは当該サイトでグローバルより先に評価される — 具体的なサイトルールが広範なグローバルルールを上書き。
ゾーン (LAN_ZONE)
ファイアウォールルールの送信元／宛先スコープとして使うインターフェースのグループ。
ICMP ID 再利用
Windows/Ubuntu は ICMP ID を約5分再利用 — 新しいルールが効かないように見えたら ping を止めて待つ。
