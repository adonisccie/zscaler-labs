Policy-Based Routing (PBR) ポリシーの構成

トラフィックを自分の思いどおりに誘導します。Adobe 用の SaaS アプリケーションオブジェクトを作成し、マッチした ICMP トラフィックを（ZIA IPSec トンネルを経由せず）そのまま WAN から送出する PBR ルールを作成して、tcpdump と iptables で実証します。

ラボ3: Policy-Based Routing (PBR) ポリシーの構成

ルーティング

Zero Trust Branch のデバイスレベルのセグメンテーションと、ZIA の AI 搭載セキュリティを組み合わせることで、包括的な Zero Trust 保護が得られます。このラボでは Policy-Based Routing (PBR) を構成してトラフィックフローを最適化します。SaaS アプリケーションのトラフィックを、ZIA IPSec トンネル経由ではなく WAN から直接 送出し、送信元サブネットとアプリケーションオブジェクトでマッチさせます。

  • 現在インターネットトラフィックが ZIA（IPSec）経由で送出されていることを検証する
  • PBR の宛先マッチとして SaaS アプリケーションオブジェクト（Adobe）を作成する
  • マッチしたトラフィックを WAN へ直接ルーティングする PBR ルール（icmp:0）を作成する
  • tcpdump と iptables -t mangle でルーティングを実証する
コース: EDU-280
版: 2.2 · 2026年2月
プラットフォーム: Skytap + Zscaler Experience Center
  • Skytap で OT Endpoint Ubuntu ホスト（VLAN30）にログインし、ip.zscaler.com にアクセスします。PBR ルールを追加する前は、トラフィックが Zscaler（ZIA）経由でルーティングされていることを確認できます。
ベースライン: ip.zscaler.com がインターネットトラフィックの Zscaler（ZIA IPSec）経由での送出を示します。

シナリオ: 送信元サブネットから Adobe SaaS オブジェクトにマッチする宛先への ICMP トラフィックを、プライマリ／セカンダリ構成の2つのゲートウェイを通じて、WAN から直接（プロトコル icmp:0）ルーティングします。

PBR シナリオ — SaaS（Adobe）の ICMP をゲートウェイ定義経由で WAN へ直接ルーティング。

3.2.1 · SaaS アプリケーションオブジェクト（Adobe）を作成

  • Policies [1] › Access Control › Segmentation › Zero Trust Branch › Objects & Groups [2] に移動します。Add [3] をクリックし、SAAS Apps [4] を選択します。
Objects & Groups › Add › SAAS Apps。
  • Rule Name: POD##-SaaS Apps [1]
  • Application name: SaaS Apps ドロップダウンから Adobe [2] を選択します。
  • Add [3] をクリックしてオブジェクトを保存します。
Adobe SaaS オブジェクトを作成 — PBR の宛先マッチとして使用します。

3.2.2 · PBR ルーティングポリシーを構成

  • Infrastructure › Connectors › Edge › Zero Trust Branch › Sites に移動し、POD##-Student-Lab を選択します。
  • Routing Policy [1] › Configure [2] を選択し、Add route をクリックします。
自分の POD サイトを開きます。
Routing Policy › Configure。
Add route。
  • Rule Name: pod##-SaaS-Apps-WAN [1]
  • Sources: Subnet/Host [2] › 10.1.10.0/24 [3] › Add [4]
  • Destinations: POD##-SaaS Apps [5]
  • Ports: Custom Port [6] › Value icmp:0 [7] › Add [8]
  • Gateway-1: pod##-student-lab-gw-1、Nexthop Type LAN/WAN [9] · Primary ge1(wan) [10] · Secondary ge2(wan) [11]
  • Gateway-2: pod##-student-lab-gw-2、Nexthop Type LAN/WAN [12] · Primary ge1(wan) [13] · Secondary ge2(wan) [14]
  • Traffic Distribution: Best [15] › Save [16] をクリック

注意: Next-hop IP は自動入力されます（例: ge1 は 100.120.1.254、ge2 は 100.130.1.254）。Distribution = Best の場合、システムは遅延・損失・ジッターなどの性能指標で WAN インターフェースを選択します。

PBR ルール: source 10.1.10.0/24 → Adobe オブジェクト、icmp:0、デュアルゲートウェイ、Best 分散。
  • Commit をクリックします。ポリシーは数秒で有効になります。
Commit — PBR が数秒でアクティブになります。
  • Interfaces [1] に移動し、WAN [2] インターフェースを選択します。アクティブユニットの best score を確認します。ここではアクティブユニットが pod01-student-lab-gw-02 で、ge1 の best score は 27 [3] です。

注意: ge1 と ge2 のスコアが同点の場合、システムは損失／遅延／ジッターで選択します。それも同一なら、負荷分散するかタイブレークルールに従います。

Interfaces › WAN — アクティブユニットの ge1 で best score 27。
  • Skytap で Windows Server VM を開き、ping adobe.com -t を実行します。想定どおり動作します。解決された IP をメモします（例: 23.54.127.40）。
Windows Server VM を開きます。
ping adobe.com -t — キャプチャ用に宛先 IP をメモします。
  • アクティブユニットの Console で、各 WAN インターフェースをキャプチャします（best score のインターフェースを使用）:
    • tcpdump -ni ge1 -c 5 host 23.54.127.40
    • tcpdump -ni ge2 -c 5 host 23.54.127.40
  • ICMP パケットは ge1（Adobe の IP）でキャプチャされ、ge2 では何もキャプチャされません。PBR ルールがトラフィックを WAN へ直接ルーティングしたことが分かります。
ge1 の tcpdump が Adobe の ICMP をキャプチャ。ge2 には何も表示されません。
  • 次にスコープを検証します。OT セグメント（VLAN30）から adobe.com に ping し（先に Windows Server の ping を止める）、その IP をメモします（例: 23.215.0.39）。
  • その IP について ge1/ge2 で tcpdump を繰り返します。ルールは送信元として VLAN10（Windows Server）だけにマッチするため、パケットはキャプチャされません。
OT（VLAN30）から Adobe へ ping。
OT トラフィックは WAN でキャプチャされません — source 10.1.10.0/24 のみがマッチ。
  • 別の SaaS アプリ（YouTube）への ping でも WAN キャプチャは得られません。宛先が Adobe オブジェクトにマッチしないためです。
YouTube への ping — Adobe 宛先オブジェクトにマッチしません。
YouTube 用に WAN インターフェースでパケットはキャプチャされません。
  • さらに Console で iptables -t mangle -nvL PBR-RULES を実行して検証します。mangle テーブルの PBR-RULES チェーンをパケット／バイトカウンター付きで一覧表示します。
    • -t mangle: mangle テーブル（PBR 用にパケットをマーク／変更）
    • -L PBR-RULES: PBR-RULES チェーンを表示 · -n: 数値表示 · -v: 詳細（インターフェース + カウンター）
iptables -t mangle -nvL PBR-RULES — マッチカウンター付きの PBR チェーン。
  • 最初の ICMP ルールにマッチが表示されます。例: 273 packets (16380 bytes)、アクション MARK set 0x802、プロトコル icmp、送信元が match-set 61、宛先が match-set 60 にマッチ。
ルール詳細: マッチした packets/bytes、MARK 0x802、送信元 match-set 61。
宛先 match-set 60 — Adobe を配信する Akamai CDN のレンジ（例: 23.32.0.0–23.67.255.255）。

完了: PBR は VLAN10 からの Adobe ICMP を、送信元 + 宛先 + ポートで正確にスコープして WAN へ直接ルーティングします。次は Microsegmentation ポリシーを構成します。

🧠
覚えておこう
PBR はマッチしたトラフィックのデフォルトルーティングを上書きします。マッチ = Source (10.1.10.0/24) + Destination (Adobe SaaS オブジェクト) + Ports (icmp:0) — すべて 一致する必要があります。Traffic Distribution: Best は遅延／損失／ジッターで WAN インターフェースを選択（ge1 スコア 27）。検証は tcpdump -ni ge1 host <ip>（ge1 でパケット、ge2 でなし）と iptables -t mangle -nvL PBR-RULES（MARK 0x802、match-set 60/61）。WAN 直接送出は ZIA の検査をバイパスするため、狭く適用すること。

Policy-Based Routing — 選択したトラフィックを、デフォルト（ZIA）経路ではなくカスタム条件でルーティング。

tcpdump -ni geX host <ip>

iptables -t mangle PBR-RULES
ルールごとの packet/byte カウンター付きで PBR チェーンを一覧表示。MARK 0x802 がマッチしたパケットをタグ付け。
match-set 60 / 61

ge1 / ge2 (WAN)
PBR がトラフィックを誘導できる2つの WAN 送出インターフェース。
