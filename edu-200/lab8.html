Lab 8: Enforce Policy with Unified DLP across Multi-Channel

LAB 8

Scenario: In this lab you will configure and test policies that protect sensitive data in motion and at rest, keeping you compliant with privacy regulations such as PCI-DSS (Payment Card Industry Data Security Standard). Using Zscaler's Unified DLP policies, you will secure multi-channel data by analyzing endpoint and SaaS application security logs.

Objectives: By the end of this lab, you will:

  • Verify and enable SSL/TLS inspection for visibility and control of data traffic.
  • Configure DLP Dictionaries, DLP Engines and DLP Rules to detect and block sensitive data, such as payment card information.
  • Test policy enforcement to confirm that DLP rules block sensitive information in data transfers.
Time: ~15 minutes
Tasks: 8.1
💭 THINK FIRST · DATA LOSS PREVENTION

DLP has three layers: a dictionary recognizes a pattern, an engine combines dictionaries into a detection, and a rule decides what happens when the engine fires.

  • Step 1 of this lab just checks that SSL Inspect All is still enabled. Why can't DLP work without it on a site like dlptoolbox.com?
    Q1 — MODEL ANSWER
    The upload goes over HTTPS. Without decryption, ZIA only sees the encrypted TLS stream: the domain from SNI and the byte counts, never the file contents. The DLP engine needs the plaintext body to find credit-card patterns. So SSL inspection (Lab 5) is the prerequisite that makes content-aware controls like DLP, sandboxing and file-type control possible at all.
  • Why separate the DLP Engine ("what sensitive data looks like") from the DLP Rule ("what to do about it")? Give an example where you'd reuse one engine in several rules.
    Q2 — MODEL ANSWER
    Detection logic changes slowly and should be defined once. Enforcement varies by context. For example, the same Sensitive Data engine could Block uploads to unsanctioned file-sharing sites for everyone, only Allow + notify the auditor for the Finance group sending to the corporate SharePoint, and also feed an endpoint or SaaS (data-at-rest) policy. If you tune the engine once, every rule improves. That's the "unified" in Unified DLP.
  • The engine's violation threshold is 1, so a single card number triggers it. What are the risks of such a low threshold, and how could you reduce false positives without missing real leaks?
    Q3 — MODEL ANSWER
    One match can come from a test number, a receipt or a random 16-digit string, so legitimate work gets blocked and users lose trust in the tool. Mitigations: raise the threshold (e.g. 5+ cards suggests a bulk export), raise the dictionary's confidence score (the Luhn check plus nearby keywords), combine dictionaries with AND (card + name/expiry), exclude known BINs, or start with Allow + auditor notification to measure before you block.
Task 8.1 Protect PII Information for Data in Motion ▾

In this task, you will create and test PII (Personally Identifiable Information) policies that safeguard data in motion, such as payment card data embedded in unsearchable PDFs or other documents.

1 Verify SSL Inspection

  1. On the Experience Center home page, type SSL/TLS Inspection in the Search menu and select the result (Internet Access > Policy).
    • Find SSL Inspect All, which you created in Lab 5.
    • Verify that its status is Enabled.
SSL Inspect All is listed with action Inspect. Bypass rules such as Office 365 One Click sit above it.

2 Create a DLP Engine

  1. On the Experience Center home page, type Dictionaries & Engines in the Search menu and select the result (Data Security > Common Resources).
  2. On the DLP Dictionaries tab:
    • Search for the Credit Cards dictionary.
    • Click the Edit button to explore its configuration.
  3. In DLP Dictionaries & Engines, go to the DLP Engines tab.
  4. Click Add DLP Engine and configure the engine:
    • Name: Sensitive Data
    • Expression: All
    • Select a Predefined Dictionary: Credit Cards
    • Violation Threshold: 1 (empty field)
    • Description: Credit Card Number and Sensitive Data Violation
  5. Click Save and Activate the changes.
The predefined Credit Cards dictionary: note the confidence score threshold and the BIN include/exclude options.
DLP Engines tab → + Add DLP Engine. Predefined engines (GLBA, HIPAA, PCI…) show the same dictionary + threshold pattern.
Engine Sensitive Data: expression ALL → Credit Cards > 1. The Channels (Endpoint, Inline Web, SaaS, Email) are what make it unified.

3 Create a DLP Rule

  1. In the Search menu, type Data Loss Prevention and select the result.
  2. Click + Add DLP Rule and configure:
    • Rule Order: 1
    • Severity: High
    • Rule Name: Data Violation Rule
    • Rule Status: Enabled
    • Content Matching: Select DLP Engines
    • DLP Engines: Sensitive Data
    • Leave all other options in Criteria and DLP Incident Receiver at their defaults.
    • Action → Data Traffic: Block
    • End User Notification: Show
  3. Click Save, then Activate the changes from the Activation icon (cloud with arrow) in the top-right corner.
Add DLP Rule: order 1, severity High, Data Violation Rule, Content Matching = Select DLP Engines → Sensitive Data.
Action → Data Traffic: Block, End User Notification: Show.

Note: You can optionally add a custom notification message: open the Notification Message drop-down, click the + (plus) icon, name it CreditCard Block, and customize the Allow and Block messages as needed.

Optional custom notification: choose which details (file name, rule name, URL category…) the user sees.
The Data Loss Prevention policy now lists Data Violation Rule → engine Sensitive Data → Block.

4 Test the policy as a user

  1. Verify ZIA activation: in Zscaler Client Connector, make sure the status for Internet Security is enabled.
  2. Test blocking sensitive data:
    • Open a browser window on the Corp Client PC.
    • Go to: https://dlptoolbox.com/
    • From the left navigation pane, select File Audit.
    • Click Choose file and pick the file Sensitive Data.txt in the DLP Test Files folder on the Desktop.
    • Click Upload.
  3. Verify the blocking behavior: confirm that a Block Notification appears during the upload, showing that the DLP rule has stopped the sensitive data from being sent.
dlptoolbox.com → File Audit → choose Sensitive Data.txt → Upload.
Blocked: "posting content to this website is not allowed", violates compliance category Sensitive Data.
🧠
MENTAL NOTE
Dictionary (Credit Cards) → Engine (Sensitive Data, under Data Security > Common Resources) → Rule (Data Violation Rule, High, Block + notify). No SSL inspection, no DLP: the upload is HTTPS. One engine can serve web, endpoint, SaaS and email channels.

QUICK REFERENCE ▲
Student FQDN
Your unique tenant domain, e.g. zs9901.labtenant.com. Used in all login IDs (student@, joe@, bev@).
Experience Center
console.zscaler.com, the unified admin console for ZIA, ZPA, ZDX and the Service Portal. This guide follows the Nav 2.0 layout: open features from the Search menu.
Service Portal
Formerly ZIdentity. The identity layer where users, groups, departments and entitlements are managed and where admins and users authenticate.
ZCC
Zscaler Client Connector, the endpoint agent that tunnels traffic to the Zero Trust Exchange.
Z-Tunnel 2.0
Network-layer tunnel that captures all IP protocols, not just web traffic. Required for Cloud Firewall.
Service Entitlement
Lets a user or group use a Zscaler service (ZIA, ZPA, ZDX) through ZCC.
Admin Entitlement
Lets a user or group administer a service in the console, scoped by a role (e.g. Executive Insights App, ZDX Read-only Admin).
SyncZPA
Additional user attribute (optional value, e.g. 123) that the lab uses to sync the user into ZPA for policy use.
Forwarding Profile
Sets the tunnel type/version and forwarding action for each network context (on-trusted, off-trusted, VPN-trusted).
Cloud App Control
SaaS/Cloud App Policy that allows or blocks individual cloud apps (e.g., allow YouTube). It is enforced ahead of URL category rules.
SSL Inspection
Trusted man-in-the-middle: ZIA decrypts, inspects and re-encrypts traffic using the Zscaler CA. The endpoint must trust the Zscaler Root CA.
Cert Pinning Bypass
A "Do Not Inspect" SSL rule for apps that check the server certificate fingerprint. It must sit above the Inspect All rule.
DLP Engine
Defines what sensitive content looks like (dictionaries + thresholds). Paired with a DLP rule that sets the action.
App Connector
ZPA software in the data center that builds outbound TLS tunnels to the ZPA cloud. No inbound firewall rules needed.
Enrollment Token
OAuth-based one-time code shown on the App Connector console (cat /etc/issue). Entered in App Connectors → Add to enroll the connector into a group.
App Segment
ZPA object that defines a private resource by domain/IP and port. Combined with an access policy, it grants ZPA access.
SIPA
Source IP Anchoring. Sends selected ZIA traffic out through a ZPA App Connector so the destination sees your organization's own egress IP.
ZDX Score
0–100 measure of end-to-end digital experience. Below 50 = Poor, 50–79 = Okay, 80 and above = Good.
Y-Engine (Analyze Score)
ZDX root-cause engine. Click a point on ZDX Score Over Time → Analyze Score to see the ranked factors (Wi-Fi, DNS, latency…) and their confidence.
ZAgent
AI assistant in the Experience Center (top-right icon). With the Digital Experience agent and Troubleshooting skill, it explains the root cause of a user's poor experience.
ZDX Probe
Synthetic test run by ZCC in the background that continuously measures DNS time, TCP connect, server response and page fetch time.
