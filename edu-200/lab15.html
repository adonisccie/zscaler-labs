Lab 15: Troubleshoot Poor Wi-Fi

LAB 15 · SDC

Scenario: As the Zscaler administrator, you are responsible for resolving a poor user experience reported by a specific employee. The user has had frequent disconnections, slow internet speeds and difficulty completing work tasks, which has hurt their productivity. Initial insights suggest that the issue may stem from poor Wi-Fi performance, but the details remain unclear. Using Zscaler Digital Experience (ZDX), your role is to analyze performance trends to pinpoint the root cause, troubleshoot the issue and restore the user's digital experience.

Objectives: By the end of this lab, you will:

  • Filter ZDX dashboards to isolate user-specific device and Wi-Fi performance data during the incident window.
  • Use the ZDX Y-Engine Analyze Score feature to find the factors that contribute to ZDX score degradation.
  • Compare Cloud Path data and diagnose a drop in ZDX score to pinpoint root causes.
  • Analyze Device Events associated with ZDX score changes to find device events that affect user experience.

💭 THINK FIRST · WI-FI ROOT CAUSE

"My internet is slow" is the hardest ticket to close, because the problem could be anywhere from the laptop's radio to the SaaS data center. You'll collect evidence from four different angles before you conclude.

  • Curtis's score swings between Good and Poor instead of being always bad. What does that on/off pattern hint at compared with a constantly poor score?
    Q1 — MODEL ANSWER
    A constant problem suggests something fixed, such as a mis-configured DNS server or a congested ISP link (compare Lab 16). An intermittent pattern suggests something that changes state: roaming between access points or SSIDs, moving away from the router, interference or a flaky adapter. That's why the lab moves from "when is it bad?" to "what changed at that moment?", using Compare to last known good and Device Events.
  • The Y-Engine says Low Wi-Fi Signal, and the Hop View shows the latency on the first hop (device → local gateway). Why is that first-hop evidence so convincing, and what does it rule out?
    Q2 — MODEL ANSWER
    The first hop is the wireless link itself, before any ISP, Zscaler Service Edge or SaaS provider is involved. If the latency appears there, then the ISP, Zscaler and Salesforce are not the cause, and no amount of tuning in those places would help. Two independent sources (an ML score explanation and a measured hop latency) agreeing makes the conclusion defensible when you hand it to the user or the desktop team.
  • Device Events show the score drops when Curtis joins Columbus-OH-Office and recovers on Google_Nest. What would you actually do with that finding?
    Q3 — MODEL ANSWER
    Tell the user specifically: "Stay on Google_Nest. Your laptop keeps hopping to the weaker Columbus-OH-Office network." Consider removing or deprioritizing that saved SSID on the device. If it's a corporate SSID, open a ticket with the network team about AP coverage or signal in that location, using the ZDX evidence. You could also check the Wi-Fi Dashboard for other users on that SSID or AP. ZDX Self-Service notifications can even warn users about poor Wi-Fi before they call.
Task 15.1 View User ZDX Score for an Application ▾

In this task, you will look up the ZDX score data for a user and an application over the period in which they've been having issues.

1 Open User / Device Search for the affected user

  1. In the Experience Center, type User Search (Digital Experience > Users) in the Search menu.
  2. In the drop-down, select Users.
  3. In the search box, type: Curtis Hardwick
  4. In the search results, click Curtis Hardwick to open the user page.
User Search: Users → Curtis Hardwick → click the result.
You land on Curtis Hardwick's Users page: device PC-CURTIS-WIFI, its details, and a score card per application.

2 Filter by time range and application

  1. View the ZDX score for an application (e.g., Salesforce Lightning) for the period of the incident:
    • Select the time period of the incident (e.g., 48 Hours).
    • Select an application (Salesforce Lightning).
    • View the ZDX Score Over Time graph.
  2. Notice that the ZDX score often swings between Good and Poor.
48 Hours + Salesforce Lightning: the score drops from Good to Poor and later recovers.

Note: You may have to pick custom options from the reporting timeframe to see meaningful data.

Task 15.2 Analyze Poor ZDX Score Interval ▾

In this task, you will zoom in on a period where the ZDX score is Poor and use the Analyze Score capability of the ZDX Y-Engine to find the key factors behind the degraded score.

Note: Your results will differ from the screenshots in the lab guide. Traffic in the lab is simulated, so the exact values and indicators vary with the time range and sample you select. Feel free to repeat these steps with different Poor score points to explore several scenarios.

1 Find a Poor score interval

  1. In the ZDX Score Over Time graph, find a time period where the ZDX Score is Poor.
Pick a point in the Poor band, here around 07:05 pm.

Note: For best results, make sure the selection includes time before and after the Poor score period.

2 Run the Y-Engine Analyze Score

  1. Click to set the cursor on a point in the graph with a Poor score.
  2. View the ZDX Score displayed for that sample.
  3. Click Analyze Score. The analysis takes a few seconds.
  4. Review the results table, titled The following factors might have impacted the ZDX score.
The sample scores 10/100. Click Analyze Score.
Y-Engine verdict: Suboptimal WiFi, performance degraded after connecting to SSID Columbus-OH-Office (100% confidence).

Note: In this example, the score of 10/100 most likely came from a Low Wi-Fi Signal, and the Suboptimal Wi-Fi hurt the user's performance after the device connected to a new SSID. (The guide text names 3Com_Wifi; the screenshot shows Columbus-OH-Office. Your SSID and values may differ.)

Task 15.3 Compare Poor ZDX Score to Last Known Good Score ▾

In this task, you will compare a Poor ZDX score sample with the last known Good score sample using the ZDX comparison tool.

1 Compare Poor vs last known Good

  1. Click Compare to for the selected point on the ZDX Score Over Time graph.
  2. Select Last known good score.
  3. Review the comparison panel, focusing on the differences between:
    • The ZDX Score for the Analyzed Point vs the Comparison Point
    • The Wi-Fi identifier
    • Client-Egress Latency
Compare to → Last known good score.
Key Differences: Wi-Fi Columbus-OH-Office vs Google_Nest, Client-Egress latency 331 ms vs 14 ms, and DNS latency far higher too.
Task 15.4 Isolate High Latency Hop ▾

In this task, you will use the Cloud Path Hop View to pinpoint where high latency occurs on the path between the user's device and the application.

1 Return to the user report and select the application

  1. Click the user Curtis Hardwick in the breadcrumb of the Compare ZDX Scores page to return to the user report.
  2. Confirm you are still viewing the affected user: Curtis Hardwick.
  3. Select the application Salesforce Lightning.
Click Curtis Hardwick in the breadcrumb to go back.

2 Focus on a Poor interval and review Cloud Path latency

  1. In the ZDX Score Over Time graph, zoom in again on a period where the ZDX Score is Poor.
  2. Scroll down to the Cloud Path graph and look at the latency values at the selected data point.
Back on the user report: Salesforce Lightning, a Poor point selected.
Cloud Path at the selected point: end-to-end latency jumps to several hundred ms.

Note: Results vary, but you'll most likely see low latency at the start of the selected period, when the ZDX score was Good, changing to high latency when the score drops to Poor.

3 Examine the Hop View to find the problem hop

  1. Below the Cloud Path graph, find the Hop View. It shows each detected hop between the client and the server for the selected application and sample, with the latency measured at each hop.
  2. Examine the hops and find the one that contributes most to the end-to-end latency.
Hop View: the first hop, device → Wi-Fi Access Point, takes 324 ms. Every later leg is small.

Note: If the network connection was lost, there is no data to report and the Hop View can't be displayed. Pick another point in time where the graph shows data.

Note: In this example, the Hop View isolates the slow end-to-end latency to the first hop, between the user's device and their local gateway.

Task 15.5 View User Device Events Associated with ZDX Score Changes ▾

In this task, you will examine User Device Events and correlate them with ZDX score changes.

1 Open the User Device Events timeline

  1. From the same user view and time window you used in the previous tasks, scroll to the bottom of the page to find the User Device Events timelines.

2 Correlate device events with the Poor score transition

  1. In the Network timeline, find the point in time where the ZDX Score changed to Poor (based on the ZDX Score Over Time graph you analyzed earlier).
  2. Mouse over the dot on the Network timeline at that time. A pop-up shows the Network Interface data recorded for that sample.
  3. Scroll through the Network Interface fields and identify what changed by looking at the values in the New Value field.
At the drop: SSID Change → Columbus-OH-Office.

Note: In this example, the SSID Change from Google_Nest to Columbus-OH-Office is associated with the Poor score transition.

3 Correlate device events with the recovery back to Good

  1. In the same Network timeline, find the dot that matches when the ZDX Score went back to Good.
  2. Mouse over that dot to view the Network Interface data for the recovery point.
At the recovery: SSID Change → Google_Nest.

Note: In the example scenario, switching back to the Google_Nest SSID is associated with a Good ZDX score, which shows the user's experience improved when they returned to the original Wi-Fi network.

4 Interpret the impact of device events

  1. Identify which Wi-Fi or network events (such as SSID changes, disconnects or signal changes) happened at the same time as the score degradation or recovery.
  2. Use this correlation to support your root-cause conclusion (e.g., "SSID changes and poor Wi-Fi signal on PC-Curtis-Wi-Fi caused the user's poor experience").
🧠
MENTAL NOTE
Four pieces of evidence, one conclusion. (1) Analyze Score → Suboptimal / Low Wi-Fi. (2) Compare to last known good → different SSID, much higher client-egress latency. (3) Hop View → latency on the first hop (device → Wi-Fi access point). (4) Device Events → SSID change at the drop and back at the recovery. Intermittent score = look for what changed.

QUICK REFERENCE ▲
Student FQDN
Your unique tenant domain, e.g. zs9901.labtenant.com. Used in all login IDs (student@, joe@, bev@).
Experience Center
console.zscaler.com, the unified admin console for ZIA, ZPA, ZDX and the Service Portal. This guide follows the Nav 2.0 layout: open features from the Search menu.
Service Portal
Formerly ZIdentity. The identity layer where users, groups, departments and entitlements are managed and where admins and users authenticate.
ZCC
Zscaler Client Connector, the endpoint agent that tunnels traffic to the Zero Trust Exchange.
Z-Tunnel 2.0
Network-layer tunnel that captures all IP protocols, not just web traffic. Required for Cloud Firewall.
Service Entitlement
Lets a user or group use a Zscaler service (ZIA, ZPA, ZDX) through ZCC.
Admin Entitlement
Lets a user or group administer a service in the console, scoped by a role (e.g. Executive Insights App, ZDX Read-only Admin).
SyncZPA
Additional user attribute (optional value, e.g. 123) that the lab uses to sync the user into ZPA for policy use.
Forwarding Profile
Sets the tunnel type/version and forwarding action for each network context (on-trusted, off-trusted, VPN-trusted).
Cloud App Control
SaaS/Cloud App Policy that allows or blocks individual cloud apps (e.g., allow YouTube). It is enforced ahead of URL category rules.
SSL Inspection
Trusted man-in-the-middle: ZIA decrypts, inspects and re-encrypts traffic using the Zscaler CA. The endpoint must trust the Zscaler Root CA.
Cert Pinning Bypass
A "Do Not Inspect" SSL rule for apps that check the server certificate fingerprint. It must sit above the Inspect All rule.
DLP Engine
Defines what sensitive content looks like (dictionaries + thresholds). Paired with a DLP rule that sets the action.
App Connector
ZPA software in the data center that builds outbound TLS tunnels to the ZPA cloud. No inbound firewall rules needed.
Enrollment Token
OAuth-based one-time code shown on the App Connector console (cat /etc/issue). Entered in App Connectors → Add to enroll the connector into a group.
App Segment
ZPA object that defines a private resource by domain/IP and port. Combined with an access policy, it grants ZPA access.
SIPA
Source IP Anchoring. Sends selected ZIA traffic out through a ZPA App Connector so the destination sees your organization's own egress IP.
ZDX Score
0–100 measure of end-to-end digital experience. Below 50 = Poor, 50–79 = Okay, 80 and above = Good.
Y-Engine (Analyze Score)
ZDX root-cause engine. Click a point on ZDX Score Over Time → Analyze Score to see the ranked factors (Wi-Fi, DNS, latency…) and their confidence.
ZAgent
AI assistant in the Experience Center (top-right icon). With the Digital Experience agent and Troubleshooting skill, it explains the root cause of a user's poor experience.
ZDX Probe
Synthetic test run by ZCC in the background that continuously measures DNS time, TCP connect, server response and page fetch time.
