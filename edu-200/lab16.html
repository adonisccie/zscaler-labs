Lab 16: Troubleshoot Slow DNS Response

LAB 16 · SDC

Scenario: A user, Linda Lucas, reports to the service desk that she has a consistently poor experience when accessing SaaS applications. Zoom calls work fine once connected, but anything web-based is very slow. Initial investigation suggests the issue may be related to slow DNS response times, which increase page load latency and degrade the user's digital experience.

Objectives: By the end of this lab, you will:

  • Use ZAgent to identify likely root causes of poor user experience.
  • View a user's overall ZDX score over time for the incident period.
  • Analyze Page Fetch Time and related Web Probe Metrics to find latency patterns.
  • Confirm the primary root cause using the ZDX Y-Engine and ZAgent.

DeviceHOST-2
Time RangeLast 48 Hours
HighlightsPoor App Experience, Slow DNS Response Times

💭 THINK FIRST · DNS & PAGE LOAD

Every new web connection starts with a DNS lookup. A slow resolver adds a delay before anything else can happen, and modern pages make dozens of lookups.

  • Linda says Zoom is fine once connected but web apps are slow. Why would slow DNS hurt web apps so much more than an established Zoom call?
    Q1 — MODEL ANSWER
    A Zoom call resolves its servers once at the start, then streams over long-lived connections, so DNS isn't in the path anymore. A SaaS web page loads many resources from many hostnames (CDNs, APIs, identity providers like Okta), and each new name needs a lookup. With a slow resolver, every one of those adds delay before the TCP/TLS handshake even starts, so Page Fetch Time rises even though bandwidth and server response are fine. "Fine once connected" is the classic DNS symptom.
  • ZAgent gives you an answer in seconds. Why does the lab still have you validate it manually with Web Probe metrics and the Y-Engine?
    Q2 — MODEL ANSWER
    An AI summary is a great starting hypothesis, but you'll have to justify the fix to someone (the network team who owns the DNS server, or the user). Seeing that DNS Resolve Time makes up most of Page Fetch Time, that PFT is roughly 2× baseline, and that the Y-Engine names High DNS with 100% confidence gives evidence you can show. It also teaches you how ZDX reaches its conclusion, so you can spot when an automated answer is incomplete.
  • The finding is that HOST-2 uses DNS server 10.0.1.53, and it's slow. What corrective actions would you suggest, and how could the work you did in Lab 7 relate?
    Q3 — MODEL ANSWER
    Hand the evidence to the team that owns 10.0.1.53: check its load, forwarders and upstream latency, add capacity or a closer resolver, or fix the DHCP option that hands it out. Check whether other users on that resolver show the same pattern (it's rarely just one person). Lab 7's lesson applies too: when ZCC steers DNS through the Zero Trust Exchange, resolution and DNS security happen in Zscaler's cloud. Make sure the steering and resolver design don't add an extra slow hop, and monitor DNS time continuously with ZDX afterwards.
Task 16.1 Use ZAgent for Root Cause Analysis ▾

In this task, you will use ZAgent to understand why Linda is experiencing poor performance.

1 Ask ZAgent

  1. On the Experience Center home page, click the ZAgent icon in the top-right corner.
  2. In the ZAgent chat:
    • Enter this prompt: Linda Lucas (linda.lucas@thezerotrustlab.com) reports to the service desk that she is having a consistently poor experience for the last 48 hours when accessing SaaS apps like Okta. Analyze the reason behind this
    • Select Agent (@): Digital Experience.
    • Select Skill (/): Troubleshooting.
    • Press Enter.
The ZAgent icon sits in the top-right toolbar.
Prompt entered, agent Digital Experience and skill Troubleshooting selected → send.

2 Review the ZAgent response

  1. Click the expand icon to view the response full screen.
  2. Find the reason ZAgent gives for Linda's poor SaaS experience.
  3. Look for any mention of DNS, latency or Page Fetch Time as contributing factors.
ZAgent runs its checks (impact window, app performance, device health, network path…) and summarizes Linda's Poor Okta experience.
Further down: the ZDX Score trend, the path from endpoint to app, and Recommended Actions such as reviewing DNS, SSL and server response telemetry.

Read it critically. In the sample response, ZAgent confirms the persistently low score but doesn't commit to a single root cause. Instead it recommends collecting connection-phase (DNS, SSL, server) metrics. That's exactly what you'll do by hand next.

Note: In the next tasks, you'll do a manual investigation with ZDX dashboards to validate ZAgent's findings and understand how ZDX reaches that conclusion.

Task 16.2 View User ZDX Score Over Time ▾

In this task, you will view Linda's overall ZDX score for the period in which she has been having issues.

1 Open Linda's user details

  1. Click View User Details in ZDX at the bottom of the response ZAgent generated.
View User Details in ZDX jumps straight to Linda's user report.

2 View the ZDX score for the incident period

  1. Select the time period of the incident (e.g., 48 Hours) and the application Okta.
  2. Click Apply filters and view the ZDX Score Over Time graph.
  3. Notice that the ZDX score is consistently Poor over the entire interval.
48 Hours + Applications Okta → Apply filters. Keep the Device Details panel in mind for Task 16.4.
Okta scores 21. The score stays in the Poor band for almost the whole 48 hours.

Note: You can also open the user from the Experience Center: type User Search in the Search menu, select Users from the drop-down, type Linda Lucas in the search box, and click the name in the results.

Task 16.3 Analyze High Page Fetch Time ▾

In this task, you will analyze the user's web probe metrics for patterns that help isolate the cause of the poor ZDX score.

1 Review Page Fetch Time

  1. From Linda's user/device report, scroll down to the Web Probe Metrics section.
  2. Review the overall range of Page Fetch Time values over the selected period. In this example, values range from about 1k ms to 60k ms, which means page loads take a long time.
  3. Click a specific point in the Page Fetch Time graph to analyze a single sample.
  4. Compare the Page Fetch Time at this point with the PFT Baseline.
One sample: Page Fetch Time ≈3989 ms vs a PFT Baseline of 732 ms, more than five times slower than normal.

Note: In the guide's example, a Page Fetch Time of 6626.5 ms is far higher than the PFT Baseline of 701 ms, which means unusually high latency per page request. Your values will differ, but the gap will be just as obvious.

2 Break down Page Fetch Time

  1. At the selected point, examine the breakdown of Page Fetch Time:
    • Server Processing Time
    • DNS Resolve Time
  2. In this example, notice:
    • High fluctuations in the DNS Resolve Time.
    • DNS Resolve Time accounts for most of the overall Page Fetch Time.
DNS Time swings wildly. This sample spends 1526 ms just resolving names.
By contrast, Server Processing Time is low and steady (≈264 ms). The app servers aren't the problem.
Availability stays at 100%: the app is up, just slow to reach.

Note: This suggests that slow or unstable DNS is a primary contributor to Linda's poor experience.

Task 16.4 Use ZDX Root Cause Analysis to Determine Root Cause ▾

In this task, you will use the ZDX Y-Engine to confirm that slow DNS is the main cause of Linda's poor ZDX score and high Page Fetch Time.

1 Run Analyze Score

  1. Scroll back up to the ZDX Score Over Time graph for Linda's device.
  2. Click Analyze Score.
  3. Review the analysis panel showing the factors that might have impacted the ZDX score during the time window.
  4. Identify the top contributing factor(s).
Analyze Score → High DNS: "High DNS resolution time detected, causing an overall increase in the page fetch time" (100%).

Note: In this example, High DNS is identified as the most likely root cause of the poor performance, with a Confidence Level of 100%.

2 Confirm and identify the DNS server

  1. Confirm that this matches your findings from Task 16.3:
    • DNS Resolve Time made up most of the Page Fetch Time.
    • DNS latency varied significantly over time.
  2. Look at the device details to find the DNS server Linda's device (HOST-2) uses: 10.0.1.53 (shown under DNS Servers (IPv4) in the Device Details panel from Task 16.2).

Conclusion: This confirms that slow DNS responses from the configured DNS server are the main cause of Linda's poor experience with SaaS applications, matching both the manual analysis and the ZAgent findings.

QUICK REFERENCE ▲
Student FQDN
Your unique tenant domain, e.g. zs9901.labtenant.com. Used in all login IDs (student@, joe@, bev@).
Experience Center
console.zscaler.com, the unified admin console for ZIA, ZPA, ZDX and the Service Portal. This guide follows the Nav 2.0 layout: open features from the Search menu.
Service Portal
Formerly ZIdentity. The identity layer where users, groups, departments and entitlements are managed and where admins and users authenticate.
ZCC
Zscaler Client Connector, the endpoint agent that tunnels traffic to the Zero Trust Exchange.
Z-Tunnel 2.0
Network-layer tunnel that captures all IP protocols, not just web traffic. Required for Cloud Firewall.
Service Entitlement
Lets a user or group use a Zscaler service (ZIA, ZPA, ZDX) through ZCC.
Admin Entitlement
Lets a user or group administer a service in the console, scoped by a role (e.g. Executive Insights App, ZDX Read-only Admin).
SyncZPA
Additional user attribute (optional value, e.g. 123) that the lab uses to sync the user into ZPA for policy use.
Forwarding Profile
Sets the tunnel type/version and forwarding action for each network context (on-trusted, off-trusted, VPN-trusted).
Cloud App Control
SaaS/Cloud App Policy that allows or blocks individual cloud apps (e.g., allow YouTube). It is enforced ahead of URL category rules.
SSL Inspection
Trusted man-in-the-middle: ZIA decrypts, inspects and re-encrypts traffic using the Zscaler CA. The endpoint must trust the Zscaler Root CA.
Cert Pinning Bypass
A "Do Not Inspect" SSL rule for apps that check the server certificate fingerprint. It must sit above the Inspect All rule.
DLP Engine
Defines what sensitive content looks like (dictionaries + thresholds). Paired with a DLP rule that sets the action.
App Connector
ZPA software in the data center that builds outbound TLS tunnels to the ZPA cloud. No inbound firewall rules needed.
Enrollment Token
OAuth-based one-time code shown on the App Connector console (cat /etc/issue). Entered in App Connectors → Add to enroll the connector into a group.
App Segment
ZPA object that defines a private resource by domain/IP and port. Combined with an access policy, it grants ZPA access.
SIPA
Source IP Anchoring. Sends selected ZIA traffic out through a ZPA App Connector so the destination sees your organization's own egress IP.
ZDX Score
0–100 measure of end-to-end digital experience. Below 50 = Poor, 50–79 = Okay, 80 and above = Good.
Y-Engine (Analyze Score)
ZDX root-cause engine. Click a point on ZDX Score Over Time → Analyze Score to see the ranked factors (Wi-Fi, DNS, latency…) and their confidence.
ZAgent
AI assistant in the Experience Center (top-right icon). With the Digital Experience agent and Troubleshooting skill, it explains the root cause of a user's poor experience.
ZDX Probe
Synthetic test run by ZCC in the background that continuously measures DNS time, TCP connect, server response and page fetch time.
