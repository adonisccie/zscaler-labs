Lab 12: Traffic Forwarding through SIPA

LAB 12

Scenario: Safemarch Corporation hosts critical cloud applications that require strict Source IP whitelisting for access. Zscaler Internet Access (ZIA) uses dynamic egress IP addresses, which can cause problems when reaching these applications. To meet these requirements, a Zscaler administrator must configure the Source IP Anchoring (SIPA) feature to ensure consistent, whitelisted source IPs for accessing public applications while using ZPA's secure connectivity.

Objectives: By the end of this lab, you will:

  • Configure a Source IP Anchoring application segment to give public applications consistent egress IPs.
  • Define and apply ZPA and ZIA forwarding rules that enable SIPA for traffic management.
  • Validate the configuration by testing traffic routing through the SIPA-enabled application.
Time: ~30 minutes
Tasks: 12.1 – 12.3
💭 THINK FIRST · SOURCE IP ANCHORING

With SIPA, ZIA still inspects the traffic, but instead of leaving the internet from a shared Zscaler IP, it hands the session to ZPA, which sends it out through your App Connector and therefore your public IP.

  • A SaaS partner only accepts logins from IPs on its allow-list. Why is "just allow-list Zscaler's egress IPs" a poor answer, and how does SIPA solve it?
    Q1 — MODEL ANSWER
    ZIA egress IPs are shared with other Zscaler customers and can change with the Service Edge the user lands on. Allow-listing them would let other tenants' users through and still break when the IP changes. SIPA steers only the chosen application from ZIA into ZPA, out through the App Connector, so the partner sees your organization's own, stable IP, and you keep ZIA's inspection and policy along the way.
  • You create two client forwarding rules for the same segment: SIPA Bypass (Client Connector → Bypass ZPA) and SIPA Forward (ZIA Service Edge → Forward to ZPA). Why both, and what would go wrong without the bypass?
    Q2 — MODEL ANSWER
    The goal is the path ZCC → ZIA → ZPA → App Connector → Internet. Without the bypass, ZCC would see ip.zscaler.com in a ZPA segment and send it straight into ZPA, skipping ZIA entirely (no inspection, no ZIA logs). SIPA Bypass tells ZCC "don't take this through ZPA, send it to ZIA". SIPA Forward then allows ZPA to accept it when it arrives from a ZIA Service Edge. Together they give exactly one path, through both services.
  • In Task 12.3 you swap ip.zscaler.com for ping.eu in the segment, and the new site's traffic is anchored without touching any ZIA rule. What does that tell you about where the "which apps get SIPA" decision lives?
    Q3 — MODEL ANSWER
    The ZIA forwarding rule and the client forwarding rules all point to the SIPA application segment (and its segment group), not to specific domains. The segment is the single source of truth: add or remove a domain there and every rule that references it follows automatically. Operationally, onboarding a new allow-listed SaaS app is a one-line change in ZPA instead of edits across several policies.
Task 12.1 Configure Source IP Anchoring (SIPA) in ZPA ▾

In this task, you will configure the SIPA feature in ZPA so public applications get a fixed, whitelisted egress IP.

1 Check the current egress IPs

  1. Find your native public IP (without ZCC):
    • Open Zscaler Client Connector (ZCC) on the Corp Client PC and disable ZIA and ZPA.
    • Open a browser and go to: ip.zscaler.com
Turn off Internet Security and Private Access in ZCC.
"…didn't come from a Zscaler IP": this is the PC's native public IP.

Note: The IP address displayed is your device's native public IP without Zscaler services active.

  1. Find your public IP after enabling Zscaler services:
    • Re-enable ZIA and ZPA in ZCC.
    • Open a browser and go to: ip.zscaler.com
Services back ON. ip.zscaler.com now reports a Zscaler (ZIA) egress IP.

Note: The IP address shown is the ZIA egress IP, which changes dynamically, as is typical of Zscaler's proxy-based architecture. Public applications, however, often need a consistent, predictable IP for security reasons. Enabling SIPA solves this, as you'll configure in the next steps.

2 Configure SIPA in ZPA

  1. Go to the ZPA Admin Portal through the Experience Center:
    • Go to Infrastructure > Private Access > App Connectors.
    • Verify that an App Connector is deployed and connected.
  2. Add a new Application Segment:
    • Go to Policies > Private Applications > Defined Application Segments.
    • Click Add Application Segment and configure it as follows: Name: SIPA Application; Source IP Anchor: Enabled; Application: ip.zscaler.com; TCP Port Ranges: 80 (HTTP) and 443 (HTTPS). Click Next.
  3. Configure the Segment Group: Name SIPA Segment, Description optional, Status Enabled. Click Next.
  4. Configure the Server Group: Name SIPA Server, App Connector Group OnPrem. Click Next.
  5. Click Save to complete the configuration.
Infrastructure → Private Access → App Connectors.
The OnPrem connector from Lab 9 is Connected. SIPA traffic will leave through it.
Name SIPA Application, Source IP Anchor: Enabled, the switch that makes this a SIPA segment.
Application: ip.zscaler.com, a public site, not a private one.
TCP ports 80 and 443.
Segment group SIPA Segment.
Server group SIPA Server → App Connector Group OnPrem.
Review, then Save.

3 Configure and save the access policy

  1. After you save the SIPA Application Segment, you are redirected to the Access Policy page. Alternatively, go to Policies > Private Applications > Access Policy.
  2. Add a new policy rule:
    • Name: SIPA Policy
    • Action: Allow Access
    • Criteria: select the applications mapped to the SIPA application segment and segment groups.
  3. Click Save.
Use Edit Policy from the wizard's Policies step.
Rule SIPA Policy: Allow Access.
Criteria: Application Segments = SIPA Application, then Save.

4 Configure the Client Forwarding Policies

  1. Rule 1, bypass ZPA for specific segment groups. Go to Infrastructure > Private Access > Client Connector Policies > Client Forwarding Policies and add a client forwarding policy:
    • Name: SIPA Bypass
    • Rule Action: Bypass ZPA
    • Criteria: Applications = map the application segments and segment groups. Client Types = Client Connector.
    • Click Add Rule.
  2. Rule 2, forward traffic to ZPA. Configure SIPA Forward:
    • Rule Action: Forward to ZPA
    • Criteria: Applications = map the application segments and segment groups. Client Types = ZIA Service Edge.
    • Click Add Rule.
Infrastructure → Private Access → Client Connector Policies → Client Forwarding Policy.
SIPA Bypass: SIPA Segment + Client Connector → Bypass ZPA.
SIPA Forward: SIPA Segment + ZIA Service Edge → Forward to ZPA.
Task 12.2 Configure ZIA Forwarding for Source IP Anchoring ▾

In this task, you will configure forwarding behavior in Zscaler Internet Access (ZIA) so that SIPA-enabled applications are routed through ZPA with consistent source IPs.

1 Define the ZPA Gateway

  1. In the Experience Center, go to Infrastructure > Internet and SaaS > Network Policies > Zscaler Private Access.
  2. Click Add Gateway for ZPA and give it a name (e.g., SIPA Gateway).
  3. Select the server group and application segment. These should be fetched automatically from the ZPA configuration in Task 12.1.
Infrastructure → Internet & SaaS → Network Policies → Zscaler Private Access.
SIPA Gateway → Server Group SIPA Server, Application Segment SIPA Application, both pulled from ZPA.

2 Configure the Forwarding Control Policy

  1. On the same page, move to the Forwarding Control Policy tab.
  2. Define the following:
    • Rule order: 1
    • Rule name: SIPA Forward
    • Make sure the rule status is enabled.
    • Under Forwarding Method, select ZPA.
Forwarding rule SIPA Forward, order 1, method ZPA.

3 Set the forwarding criteria

  1. Go to the Criteria tab.
  2. Click Destination and define the ZPA application segment (e.g., SIPA Application).
  3. Set the Forward to ZPA Gateway action to the SIPA Gateway you defined earlier.
  4. Click Save, then Activate the changes.
Destination: ZPA Application Segment SIPA Application → Forward to ZPA Gateway SIPA Gateway.
Activate the ZIA change.
Task 12.3 Verify Source IP Anchoring (SIPA) Functionality ▾

In this task, you will verify that the SIPA configuration works correctly by confirming that traffic is routed through ZPA, and see what happens when you change the application segment.

1 Do an initial check

  1. Open a browser on the Corp Client PC and go to: ip.zscaler.com
  2. Look at the public IP address shown. This IP confirms that traffic is routed from ZIA to ZPA to the App Connector, as defined in the SIPA rule.
ip.zscaler.com now sees the App Connector's public IP: the anchored source IP.

Note: The SIPA IP shown is different from the default ZIA egress IP (Step 1 of Task 12.1). This shows that ZPA can give a fixed source IP to selected applications, which is essential for whitelisting security.

2 Dynamic testing (modify the application segment)

  1. Go to the ZPA Admin Portal through the Experience Center: Policies > Private Application > Defined Application Segments.
  2. Edit the SIPA Application segment as follows:
    • Remove ip.zscaler.com from the Application tab.
    • Add a new domain (e.g., ping.eu) instead.
Edit the SIPA Application segment.
Swap the application to ping.eu and save.

3 Test the dynamic configuration

  1. Open a browser and go to: ping.eu
  2. Look at the new IP address shown by ping.eu.
ping.eu now reports the anchored IP too. No ZIA rule had to change.

Note: Traffic for the newly defined application is routed through ZPA-SIPA and shows the updated ZPA egress IP.

🧠
MENTAL NOTE
Path: ZCC → ZIA → ZPA → App Connector → Internet. ZPA: segment SIPA Application (Source IP Anchor on, 80/443) + SIPA Segment/Server + SIPA Policy. Client forwarding: SIPA Bypass (Client Connector) + SIPA Forward (ZIA Service Edge). ZIA: SIPA Gateway + forwarding rule (method ZPA) + Activate. To change which apps are anchored, edit the segment.

Student FQDN
Your unique tenant domain, e.g. zs9901.labtenant.com. Used in all login IDs (student@, JoeSupport@, BevIT@).
Experience Center
console.zscaler.com, the unified admin console for ZIA, ZPA, ZDX and the Service Portal. This lab uses the Nav 1.0 (Original) layout.
Service Portal
Formerly ZIdentity. The identity layer where users, groups, departments and entitlements are managed and where admins and users authenticate.
ZCC
Zscaler Client Connector, the endpoint agent that tunnels traffic to the Zero Trust Exchange.
Z-Tunnel 2.0
Network-layer tunnel that captures all IP protocols, not just web traffic. Required for Cloud Firewall.
Service Entitlement
Lets a user or group use a Zscaler service (ZIA, ZPA, ZDX) through ZCC.
Admin Entitlement
Lets a user or group administer a service in the console, scoped by a role (e.g. Executive Insights App, ZDX Read-only Admin).
SyncZPA
Additional user attribute (optional value, e.g. 123) that the lab uses to sync the user into ZPA for policy use.
Forwarding Profile
Sets the tunnel type/version and forwarding action for each network context (on-trusted, off-trusted, VPN-trusted).
Cloud App Control
Application-layer policy that identifies apps by DPI (e.g., WhatsApp) regardless of port. Separate from Firewall Filtering.
SSL Inspection
Trusted man-in-the-middle: ZIA decrypts, inspects and re-encrypts traffic using the Zscaler CA. The endpoint must trust the Zscaler Root CA.
Cert Pinning Bypass
A "Do Not Inspect" SSL rule for apps that check the server certificate fingerprint. It must sit above the Inspect All rule.
DLP Engine
Defines what sensitive content looks like (dictionaries + thresholds). Paired with a DLP rule that sets the action.
App Connector
ZPA software in the data center that builds outbound TLS tunnels to the ZPA cloud. No inbound firewall rules needed.
Enrollment Token
OAuth-based one-time code shown on the App Connector console (cat /etc/issue). Entered in App Connectors → Add to enroll the connector into a group.
App Segment
ZPA object that defines a private resource by domain/IP and port. Combined with an access policy, it grants ZPA access.
SIPA
Source IP Anchoring. Sends selected ZIA traffic out through a ZPA App Connector so the destination sees your organization's own egress IP.
ZDX Score
0–100 measure of end-to-end digital experience. Below 50 = Poor, 50–79 = Okay, 80 and above = Good.
Y-Engine (Analyze Score)
ZDX root-cause engine. Click a point on ZDX Score Over Time → Analyze Score to see the ranked factors (Wi-Fi, DNS, latency…) and their confidence.
ZDX Copilot
AI assistant in ZDX that answers natural-language questions and summarizes root cause for a user's experience issue.
ZDX Probe
Synthetic test run by ZCC in the background that continuously measures DNS time, TCP connect, server response and page fetch time.
