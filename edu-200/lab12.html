Lab 12: Traffic Forwarding through SIPA

LAB 12

Scenario: Safemarch Corporation hosts critical cloud applications that require strict Source IP whitelisting for access. Zscaler Internet Access (ZIA) uses dynamic egress IP addresses, which can cause problems when reaching these applications. To meet these requirements, a Zscaler administrator must configure the Source IP Anchoring (SIPA) feature to ensure consistent, whitelisted source IPs for accessing public applications while using ZPA's secure connectivity.

Objectives: By the end of this lab, you will:

  • Configure a Source IP Anchoring application segment to give public applications consistent egress IPs.
  • Define and apply ZPA and ZIA forwarding rules that enable SIPA for traffic management.
  • Validate the configuration by testing traffic routing through the SIPA-enabled application.
Time: ~30 minutes
Tasks: 12.1 – 12.3
💭 THINK FIRST · SOURCE IP ANCHORING

With SIPA, ZIA still inspects the traffic, but instead of leaving the internet from a shared Zscaler IP, it hands the session to ZPA, which sends it out through your App Connector and therefore your public IP.

  • A SaaS partner only accepts logins from IPs on its allow-list. Why is "just allow-list Zscaler's egress IPs" a poor answer, and how does SIPA solve it?
    Q1 — MODEL ANSWER
    ZIA egress IPs are shared with other Zscaler customers and can change with the Service Edge the user lands on. Allow-listing them would let other tenants' users through and still break when the IP changes. SIPA steers only the chosen application from ZIA into ZPA, out through the App Connector, so the partner sees your organization's own, stable IP, and you keep ZIA's inspection and policy along the way.
  • You create two client forwarding rules for the same segment: SIPA Bypass (Client Connector → Bypass ZPA) and SIPA Forward (ZIA Service Edge → Forward to ZPA). Why both, and what would go wrong without the bypass?
    Q2 — MODEL ANSWER
    The goal is the path ZCC → ZIA → ZPA → App Connector → Internet. Without the bypass, ZCC would see ip.zscaler.com in a ZPA segment and send it straight into ZPA, skipping ZIA entirely (no inspection, no ZIA logs). SIPA Bypass tells ZCC "don't take this through ZPA, send it to ZIA". SIPA Forward then allows ZPA to accept it when it arrives from a ZIA Service Edge. Together they give exactly one path, through both services.
  • In Task 12.3 you swap ip.zscaler.com for ping.eu in the segment, and the new site's traffic is anchored without touching any ZIA rule. What does that tell you about where the "which apps get SIPA" decision lives?
    Q3 — MODEL ANSWER
    The ZIA forwarding rule and the client forwarding rules all point to the SIPA application segment (and its segment group), not to specific domains. The segment is the single source of truth: add or remove a domain there and every rule that references it follows automatically. Operationally, onboarding a new allow-listed SaaS app is a one-line change in ZPA instead of edits across several policies.
Task 12.1 Configure Source IP Anchoring (SIPA) in ZPA ▾

In this task, you will configure the SIPA feature in ZPA to provide a fixed, whitelisted egress IP for public applications.

1 Verify the current egress IPs

  1. Identify your native public IP (without ZCC):
    • Open Zscaler Client Connector (ZCC) on the Corp Client PC and turn off ZIA (Internet Security) and ZPA (Private Access).
    • Open a browser and go to: ip.zscaler.com
Turn off Internet Security and Private Access in ZCC.
With ZCC off, ip.zscaler.com says you're not going through Zscaler and shows your native public IP.

Note: The IP address displayed is your device's native public IP without Zscaler services active.

2 Identify your public IP with Zscaler services enabled

  1. Turn ZIA and ZPA back on in ZCC.
  2. Open a browser and go to: ip.zscaler.com
Internet Security → Turn On.
Private Access → Turn On.
Now the request arrives from a Zscaler (ZIA) egress IP. ip.zscaler.com also shows the proxy's virtual IP and your original source IP.

Note: The IP address shown is the ZIA egress IP, which changes dynamically, as is typical of Zscaler's proxy-based architecture. Public applications, however, often need a consistent, predictable IP for security reasons. Enabling SIPA solves this, as you'll configure in the next steps.

3 Configure SIPA in ZPA: check the App Connector

  1. On the Experience Center home page, type App Connector in the Search menu and select the result (Private Access > Private Infrastructure > App Connectors).
    • Verify that an App Connector is deployed and Connected.
The OnPrem connector from Lab 9 shows Connected. SIPA traffic will leave the internet from here.

4 Add the SIPA Application Segment

  1. Type Application Segments in the Search menu.
  2. Click Add Application Segment and configure it as follows:
    • Name: SIPA Application
    • Source IP Anchor: Enabled
    • Application: ip.zscaler.com
    • TCP Port Ranges: 80 (HTTP) and 443 (HTTPS)
    • Click Next.
Name SIPA Application, Source IP Anchor: Enabled, application ip.zscaler.com.
TCP port ranges 80–80 and 443–443 → Next.

5 Segment Group, Server Group and Save

  1. Configure the Segment Group:
    • Click Add Segment Group.
    • Name: SIPA Segment
    • Description: optional
    • Status: Enabled
    • Click Next.
  2. Configure the Server Group:
    • Click Add Server Group.
    • Name: SIPA Server
    • App Connector Group: OnPrem
    • Click Next.
  3. Click Save to complete the configuration.
New segment group SIPA Segment.
New server group SIPA Server through App Connector Group OnPrem.
Review: SIPA Application → SIPA Segment → SIPA Server → OnPrem. Click Save.

6 Configure and save the Access Policy

  1. After saving the SIPA Application Segment, click Edit Policy.
  2. Add a new policy rule:
    • Click Add Rule.
    • Action: Allow Access
    • Rule Name: SIPA Policy
    • Define the criteria: click Add Criteria and select Applications. Click Add Application Segments and select SIPA Application, then click Add Segment Groups and select SIPA Segment.
  3. Click Add Rule.
Use Edit Policy from the wizard's Policies step.
Access rule SIPA Policy: Allow Access to the SIPA Application segment / SIPA Segment group.

7 Configure Client Forwarding Policies

  1. Rule 1: Bypass ZPA for the SIPA segment from Client Connector
    • In the Search menu, type Client Forwarding Policy.
    • Add a Client Forwarding Policy rule:
    • Rule Action: Bypass ZPA
    • Rule Name: SIPA Bypass
    • Criteria: click Add Criteria → Applications. Add Application Segments → SIPA Application, and Add Segment Groups → SIPA Segment.
    • Click Add Criteria → Client Types, and select Client Connector.
    • Click Add Rule.
  2. Rule 2: Forward traffic to ZPA from the ZIA Service Edge
    • Rule Action: Forward to ZPA
    • Rule Name: SIPA Forward
    • Criteria: click Add Criteria → Applications. Add Application Segments → SIPA Application, and Add Segment Groups → SIPA Segment.
    • Click Add Criteria → Client Types, and select ZIA Service Edge.
    • Click Add Rule.
Rule 1, SIPA Bypass: Bypass ZPA when the client type is Client Connector.
Rule 2, SIPA Forward: Forward to ZPA when the client type is ZIA Service Edge.
Task 12.2 Configure ZIA Forwarding for Source IP Anchoring ▾

In this task, you will configure forwarding in Zscaler Internet Access (ZIA) so that SIPA-enabled applications are routed through ZPA with consistent source IPs.

1 Define the ZPA Gateway

  1. On the Experience Center home page, type Private Access GW in the Search menu and select the result (Infrastructure > Internet & SaaS).
  2. Click Add Gateway for ZPA and enter a Gateway Name (e.g., SIPA Gateway).
  3. Select the Server Group and Application Segment. They are fetched automatically from the ZPA configuration you made in Task 12.1.
  4. Click Save.
Gateway SIPA Gateway → Server Group SIPA Server, which brings in the SIPA Application segment.

2 Configure the Forwarding Control Policy

  1. Search for Forwarding Control in the Search menu and select it.
  2. Click Add Rule and define the following:
    • Rule Name: SIPA Forward
    • Rule Order: 1
    • Rule Status: Enabled
    • Forwarding Method: ZPA
    • Criteria: click Add Criteria and select ZPA Application Segment. Click Any and select SIPA Application.
    • Set the Forward to ZPA Gateway action to the SIPA Gateway you defined earlier.
  3. Click Save, then Activate the changes.
Forwarding rule SIPA Forward: destination ZPA Application Segment = SIPA Application, method ZPA, gateway SIPA Gateway.
Rule saved. Open the activation icon and click Activate.
Task 12.3 Verify Source IP Anchoring (SIPA) Functionality ▾

In this task, you will verify that SIPA works by confirming traffic is routed through ZPA, and see what happens when you change the application segment.

1 Perform the initial verification

  1. Open a browser on the Corp Client PC and go to: ip.zscaler.com
  2. Look at the public IP address displayed. This IP confirms that traffic is routed from ZIA to ZPA to the App Connector, as defined in the SIPA rule.
ip.zscaler.com now sees the App Connector's public IP, not the ZIA egress IP from Step 2.

Note: The SIPA IP shown is different from the default ZIA egress IP (Step 2 of Task 12.1). This shows that ZPA can give a fixed source IP to selected applications, which is essential for whitelisting security.

Why does it match my native IP? In this lab the App Connector sits on the same network as the Corp Client PC, so the anchored IP is the same one you saw with ZCC turned off. In production, the connector's site (a data center or cloud VPC) provides the fixed IP that partners put on their allow-lists.

2 Dynamic testing: modify the application segment

  1. Type Application Segments in the Search menu and click Application Segments.
  2. Edit the SIPA Application segment as follows:
    • Remove ip.zscaler.com from the Applications section.
    • Add a new domain instead (e.g., ping.eu).
    • Click Save.
Defined Application Segments → Edit (pencil) on SIPA Application.
Replace ip.zscaler.com with ping.eu, then Save.

3 Test the dynamic configuration

  1. Open a browser and go to: ping.eu
  2. Look at the IP address that ping.eu displays.
ping.eu now reports the anchored IP. No ZIA rule was touched: the segment decides which apps get SIPA.

Note: Traffic for the newly defined application is routed through ZPA-SIPA and shows the updated ZPA egress IP.

🧠
MENTAL NOTE
Path: ZCC → ZIA → ZPA → App Connector → Internet. ZPA: segment SIPA Application (Source IP Anchor on, 80/443) + SIPA Segment/Server + SIPA Policy. Client forwarding: SIPA Bypass (Client Connector) + SIPA Forward (ZIA Service Edge). ZIA: Private Access GW → SIPA Gateway + Forwarding Control rule (method ZPA) + Activate. To change which apps are anchored, edit the segment.

Student FQDN

Experience Center
console.zscaler.com, the unified admin console for ZIA, ZPA, ZDX and the Service Portal. This guide follows the Nav 2.0 layout: open features from the Search menu.
Service Portal
Formerly ZIdentity. The identity layer where users, groups, departments and entitlements are managed and where admins and users authenticate.
ZCC
Zscaler Client Connector, the endpoint agent that tunnels traffic to the Zero Trust Exchange.
Z-Tunnel 2.0
Network-layer tunnel that captures all IP protocols, not just web traffic. Required for Cloud Firewall.
Service Entitlement
Lets a user or group use a Zscaler service (ZIA, ZPA, ZDX) through ZCC.
Admin Entitlement
Lets a user or group administer a service in the console, scoped by a role (e.g. Executive Insights App, ZDX Read-only Admin).
SyncZPA
Additional user attribute (optional value, e.g. 123) that the lab uses to sync the user into ZPA for policy use.
Forwarding Profile
Sets the tunnel type/version and forwarding action for each network context (on-trusted, off-trusted, VPN-trusted).
Cloud App Control
SaaS/Cloud App Policy that allows or blocks individual cloud apps (e.g., allow YouTube). It is enforced ahead of URL category rules.
SSL Inspection
Trusted man-in-the-middle: ZIA decrypts, inspects and re-encrypts traffic using the Zscaler CA. The endpoint must trust the Zscaler Root CA.
Cert Pinning Bypass
A "Do Not Inspect" SSL rule for apps that check the server certificate fingerprint. It must sit above the Inspect All rule.
DLP Engine
Defines what sensitive content looks like (dictionaries + thresholds). Paired with a DLP rule that sets the action.
App Connector
ZPA software in the data center that builds outbound TLS tunnels to the ZPA cloud. No inbound firewall rules needed.
Enrollment Token
OAuth-based one-time code shown on the App Connector console (cat /etc/issue). Entered in App Connectors → Add to enroll the connector into a group.
App Segment
ZPA object that defines a private resource by domain/IP and port. Combined with an access policy, it grants ZPA access.
SIPA
Source IP Anchoring. Sends selected ZIA traffic out through a ZPA App Connector so the destination sees your organization's own egress IP.
ZDX Score
0–100 measure of end-to-end digital experience. Below 50 = Poor, 50–79 = Okay, 80 and above = Good.
Y-Engine (Analyze Score)
ZDX root-cause engine. Click a point on ZDX Score Over Time → Analyze Score to see the ranked factors (Wi-Fi, DNS, latency…) and their confidence.
ZAgent
AI assistant in the Experience Center (top-right icon). With the Digital Experience agent and Troubleshooting skill, it explains the root cause of a user's poor experience.
ZDX Probe
Synthetic test run by ZCC in the background that continuously measures DNS time, TCP connect, server response and page fetch time.
