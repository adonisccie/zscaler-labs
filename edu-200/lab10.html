Lab 10: Add a Corporate Application

LAB 10

Scenario: Safemarch Corporation needs secure, scalable access to several internal applications that share a common domain pattern. To simplify access management and enforce reliable Zero Trust policies, you will configure a wildcard application segment for general access and a dedicated application segment for more granular user and application access. You will also enable ICMP access for troubleshooting.

Objectives: By the end of this lab, you will:

  • Configure a wildcard application segment for internal applications (e.g., *.patraining.safemarch.com).
  • Configure user-specific access to defined internal applications.
  • Enable ICMP access for troubleshooting in the ZPA Admin Portal.
Time: ~35 minutes
Tasks: 10.1 – 10.3
💭 THINK FIRST · APPLICATION SEGMENTS

In ZPA nothing is reachable until it's defined. An application segment says what (domains and ports), a server group says through which connectors, and an access policy says who.

  • The Discovery segment covers *.patraining.safemarch.com on almost every port. That's convenient. Why is it a starting point and not where a mature zero-trust deployment should stay?
    Q1 — MODEL ANSWER
    A broad wildcard recreates a "flat network" feel: any allowed user can reach any host and port under that domain. That's great for discovery (finding out which apps people actually use, shown in Analytics → Private Applications), but it isn't least privilege. The mature path, which Task 10.2 starts, is to turn discovered apps into specific segments (one app, its real ports) with user- or group-scoped policies, then shrink or retire the wildcard.
  • The intranet host matches both the wildcard segment and the new Intranet segment. Which one does ZPA use, and why does that let you restrict the intranet to the Student user?
    Q2 — MODEL ANSWER
    ZPA uses the most specific match. A fully qualified intranet.patraining.safemarch.com beats *.patraining.safemarch.com. Requests to the intranet are therefore judged against the policies attached to the Intranet segment (the Allow Intranet rule with loginname = Student), not the broad Discovered Apps rule. Other users who only match the wildcard rule won't get the intranet. That's how a specific segment "carves out" tighter control.
  • Even after access works, ping intranet… fails until you enable ICMP Access on the segment. Why is ICMP off by default for private apps?
    Q3 — MODEL ANSWER
    Users need the application, not the ability to probe hosts. ICMP is a classic reconnaissance tool for discovering live machines, so leaving it off keeps the private network dark even to authenticated users. Enable it only on the segments where operations staff need ping for troubleshooting. That's another small application of least privilege.
Task 10.1 Configure a Wildcard Application Segment for Internal Applications ▾

In this task, you will configure a wildcard application segment that discovers internal applications matching a domain pattern and allows general access for all users.

1 Add a Wildcard Application Segment: Define Applications

  1. From the Experience Center, go to Policies > Access Control > Private Applications > Defined Application Segments.
  2. Click +Add Application Segment to create a new segment.
  3. At the Define Applications step of the wizard, under General Information:
    • Name: Discovery
    • Status: Enabled
    • Source IP Anchor: Disabled
    • Add a suitable description.
  4. Applications: in the Enter a domain or IP address field, enter *.patraining.safemarch.com
  5. Client Connector Access: define the port ranges for TCP and UDP:
    • TCP Port Ranges: 2-52 and 54-65535
    • UDP Port Ranges: 1-52 and 54-65535
    • TCP Keepalive: set to Disabled.
  6. Common Configuration: leave the defaults as they are.
Private Applications → App Segments → Add Application Segment.
General Information: name Discovery, status Enabled.
Applications: *.patraining.safemarch.com.
TCP 2-52, 54-65535 and UDP 1-52, 54-65535. Port 53 (DNS) is deliberately left out.

2 Additional Configuration, Segment Group and Server Group

  1. At the Additional Configuration step, leave these options unchanged, then click Next:
    • Double Encryption: Disabled
    • Bypass: Use Client Forwarding Policy
    • ICMP Access: Disabled
  2. At the Segment Group step:
    • Click Add Segment Group.
    • Name: Discovered Apps
    • Status: Enabled
    • Click Next.
  3. Add Server Group:
    • Name: CorpServers
    • Status: Enabled
    • Set Dynamic Server Discovery: Enabled.
    • App Connector Groups: OnPrem.
    • Click Next.

Note: The ICMP Access option is usually left disabled unless ICMP connectivity is needed for application troubleshooting or testing.

Additional Configuration: Double Encryption Disabled, ICMP Access Disabled, Bypass Use Client Forwarding Policy.
New segment group Discovered Apps.
New server group CorpServers: Dynamic Server Discovery on, through App Connector Group OnPrem (Lab 9).

3 Review

  1. At the Review step, check the configuration and click Save.
Review: Discovery → Discovered Apps → CorpServers → OnPrem. Click Save.

4 Configure Access Policies

  1. Go to the Policies > Access Policy page in the ZPA Admin Portal.
  2. On the Access Policy page, click Add and configure the new rule:
    • Name: Discovered Apps
    • Rule Action: Allow Access
    • Leave App Connector Selection Method at All App Connector Groups for the Application.
    • Click Add Criteria, select Applications, and choose the Discovered Apps Segment Group.
    • Don't add any other criteria.
    • Click Save.
After saving, the wizard's Policies step offers Edit Policy, a shortcut to the Access Policy page.
Rule Discovered Apps, Rule Action Allow Access.
Add Criteria → Applications. Connector selection stays All App Connector groups for the application.
Criteria: Segment Groups = Discovered Apps, then Save.

5 Test the Access Policy

  1. On the Corp Client PC, open a web browser in a window.
  2. Open the Zscaler Client Connector and place its window next to the browser.
  3. Load http://intranet.patraining.safemarch.com (a bookmark is provided).
  4. Confirm that the Intranet page loads correctly.
  5. Refresh the page and check that the Total Bytes Sent / Received counters in Zscaler Client Connector go up.
The intranet loads, and ZCC's Private Access byte counters rise, so the traffic is going through ZPA.
Task 10.2 Configure User-Specific Access to an Intranet Application ▾

In this task, you will create a dedicated application segment for more granular access control that limits intranet access to the "Student" user.

1 Review recently accessed private applications

  1. From the Experience Center, go to the search bar and type applications to navigate to Analytics > Private Applications.
  2. Scroll to the Applications Discovered in the past 14 days section to identify recently accessed applications.
Search applications → Analytics → Private Applications.
The Private Applications dashboard shows what users reached through ZPA.

2 Configure the Intranet Application Segment

  1. Click Add Application Segment, select the application intranet.patraining.safemarch.com, and click Define Selected Applications.
    • Alternatively, go to Policies > App Segment.
  2. At the Define Applications step:
    • Name: Intranet
    • Status: Enabled
    • Source IP Anchor: Disabled
    • Add a suitable description.
    • Leave the other settings at their defaults.
    • Click Next.
  3. Add a Segment Group as follows:
    • Name: CorpApps
    • Status: Enabled
    • Click Next.
  4. Add the Server Group as follows:
    • Name: CorpServers (select the one you created for the wildcard application segment)
    • Click Next.
  5. Click Save.
Under Applications Discovered in Past 14 Days, select the intranet host → Add Application Segment.
Name Intranet, Enabled.
Keep the defaults for the remaining settings and click Next.
New segment group CorpApps.
Select Server Group → reuse CorpServers.

Note: After you save the Application Segment, you are redirected to the Edit Policy page, where you can add a policy for the App Segment. Alternatively, go directly to the Policies > Access Policy page from the left-hand menu.

The Policies step lists the existing Discovered Apps rule. Click Edit Policy to add a new one.

3 Add an Access Policy

  1. Go to Policies > Access Policy. Click Add to configure a new policy with these settings:
    • Rule Name: Allow Intranet
    • Rule Action: Allow Access
    • Keep the App Connector Selection Method: All App Connector Groups.
  2. Define the criteria:
    • Click Add Criteria.
    • Select Applications, and choose the Intranet Application Segment you just created.
    • Add another criterion for User and Session Attributes: click the + icon to add User Attributes, then select loginname and choose the user student@<Student FQDN>.
    • Click Save.
Rule Allow Intranet, Allow Access, all App Connector groups.
Add Criteria → Applications.
Application Segments = Intranet.
Add Criteria → User and Session Attributes.
Click + → User Attributes.
loginname = your student@… user, then Save. Only Student is allowed into the Intranet segment.

4 Test the policy

  1. On the Corp Client PC, open a web browser and Zscaler Client Connector side by side so you can watch the traffic counters as pages load.
  2. Go to http://intranet.patraining.safemarch.com using the provided bookmark.
  3. Make sure the intranet page loads successfully for the Student user.
  4. Refresh the page and confirm that the Total Bytes Sent/Received counters in Zscaler Client Connector go up.
Student still gets the intranet, now through the dedicated Intranet segment and Allow Intranet rule.
Task 10.3 Enable ICMP Access ▾

In this task, you will enable ICMP access on an application segment so you can use ping to troubleshoot reachability to an internal application.

1 Verify ICMP accessibility

  1. On the Corp Client PC, open Command Prompt and enter: ping intranet.patraining.safemarch.com
With ICMP Access disabled, ping times out (100% loss) even though HTTP works.

Note: If ICMP Access is disabled in the Application Segment, the internal application won't respond to ping requests or be reachable through ICMP.

2 Enable ICMP Access in the ZPA Admin Portal

  1. Go to Policies > Access Control > Private Applications > Defined Application Segments.
  2. Find the Application Segment named Intranet and click Edit.
  3. In the Edit Application Segment window, click Next to reach the ICMP Access field.
  4. Set ICMP Access to Enabled.
  5. Click Save to apply the change.
App Segments list: Edit (pencil) on the Intranet segment.
ICMP Access: Enabled, then Save.

3 Test ICMP connectivity

  1. Return to the Corp Client PC.
  2. Reopen Command Prompt and enter ping intranet.patraining.safemarch.com
With ICMP Access enabled, the intranet now replies to ping.

Expected Result: The internal application should now respond to ping requests, which confirms that ICMP traffic is allowed.

Note: Only enable the ICMP Access option if ICMP connectivity is needed for troubleshooting. Avoid using it for general application testing.

🧠
MENTAL NOTE
Segment → Segment Group → Server Group → Connector Group → Access Policy. Wildcard Discovery (*.patraining.safemarch.com) + Discovered Apps rule = broad access and app discovery. Specific Intranet segment + Allow Intranet (loginname = Student) = least privilege, because the most specific segment wins. ICMP Access is off by default, so enable it per segment only when ping is needed.

QUICK REFERENCE ▲
Student FQDN
Your unique tenant domain, e.g. zs9901.labtenant.com. Used in all login IDs (student@, JoeSupport@, BevIT@).
Experience Center
console.zscaler.com, the unified admin console for ZIA, ZPA, ZDX and the Service Portal. This lab uses the Nav 1.0 (Original) layout.
Service Portal
Formerly ZIdentity. The identity layer where users, groups, departments and entitlements are managed and where admins and users authenticate.
ZCC
Zscaler Client Connector, the endpoint agent that tunnels traffic to the Zero Trust Exchange.
Z-Tunnel 2.0
Network-layer tunnel that captures all IP protocols, not just web traffic. Required for Cloud Firewall.
Service Entitlement
Lets a user or group use a Zscaler service (ZIA, ZPA, ZDX) through ZCC.
Admin Entitlement
Lets a user or group administer a service in the console, scoped by a role (e.g. Executive Insights App, ZDX Read-only Admin).
SyncZPA
Additional user attribute (optional value, e.g. 123) that the lab uses to sync the user into ZPA for policy use.
Forwarding Profile
Sets the tunnel type/version and forwarding action for each network context (on-trusted, off-trusted, VPN-trusted).
Cloud App Control
Application-layer policy that identifies apps by DPI (e.g., WhatsApp) regardless of port. Separate from Firewall Filtering.
SSL Inspection
Trusted man-in-the-middle: ZIA decrypts, inspects and re-encrypts traffic using the Zscaler CA. The endpoint must trust the Zscaler Root CA.
Cert Pinning Bypass
A "Do Not Inspect" SSL rule for apps that check the server certificate fingerprint. It must sit above the Inspect All rule.
DLP Engine
Defines what sensitive content looks like (dictionaries + thresholds). Paired with a DLP rule that sets the action.
App Connector
ZPA software in the data center that builds outbound TLS tunnels to the ZPA cloud. No inbound firewall rules needed.
Enrollment Token
OAuth-based one-time code shown on the App Connector console (cat /etc/issue). Entered in App Connectors → Add to enroll the connector into a group.
App Segment
ZPA object that defines a private resource by domain/IP and port. Combined with an access policy, it grants ZPA access.
SIPA
Source IP Anchoring. Sends selected ZIA traffic out through a ZPA App Connector so the destination sees your organization's own egress IP.
ZDX Score
0–100 measure of end-to-end digital experience. Below 50 = Poor, 50–79 = Okay, 80 and above = Good.
Y-Engine (Analyze Score)
ZDX root-cause engine. Click a point on ZDX Score Over Time → Analyze Score to see the ranked factors (Wi-Fi, DNS, latency…) and their confidence.
ZDX Copilot
AI assistant in ZDX that answers natural-language questions and summarizes root cause for a user's experience issue.
ZDX Probe
Synthetic test run by ZCC in the background that continuously measures DNS time, TCP connect, server response and page fetch time.
