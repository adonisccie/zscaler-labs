Lab 13: Access an Internal Application using Remote Desktop Protocol (RDP)

LAB 13 · OPTIONAL

Scenario: An internal user reports that they can't access the internal application intranet.patraining.safemarch.com. As the Zscaler administrator, you start troubleshooting by confirming application connectivity through ICMP Access. With basic connectivity confirmed, you try to connect to the application using Remote Desktop Protocol (RDP), which requires TCP port 3389. Reviewing the application segment configuration, you find that port 3389 is not included in the defined TCP port ranges, so ZPA doesn't forward RDP traffic. To fix this, you will update the application segment to include port 3389 and confirm secure access with RDP.

Objectives: By the end of this lab, you will:

  • Configure the Intranet Application Segment in ZPA to allow RDP access on port 3389 for troubleshooting, connecting securely through ZPA.
  • Verify the access details in the logs.
Time: ~10 minutes
Tasks: 13.1
💭 THINK FIRST · PORTS IN APP SEGMENTS

An application segment defines a host and the ports ZPA will carry for it. The browser works and ping works, yet RDP fails. Same host, different port.

  • In Lab 10 you enabled ICMP and HTTP worked, so the host is clearly reachable. Why does ZPA still refuse RDP to the same host, and why is that the intended behavior?
    Q1 — MODEL ANSWER
    ZPA grants access per application = host + port, not per host. The Intranet segment only lists the web ports, so a request to :3389 doesn't match any segment the user is allowed. ZPA has nothing to forward, and Diagnostics records a policy block. That's least privilege by design: being allowed to browse a server doesn't mean being allowed to log in to its desktop.
  • netstat -fn shows an Established connection on 3389, but the remote address isn't the server's real 10.0.0.x IP. What is the client actually connected to, and why?
    Q2 — MODEL ANSWER
    ZCC answers DNS for ZPA-defined apps with a synthetic IP (typically in the 100.64.0.0/10 range), and the client "connects" to that local address. ZCC intercepts the session and carries it through the ZPA tunnel to the App Connector, which opens the real connection to the server. The client never learns or routes to the data-center IP, so the network stays hidden even from authenticated users.
  • Opening RDP to a server is powerful. In production, how would you make sure only the right admins get port 3389, rather than everyone who can reach the intranet?
    Q3 — MODEL ANSWER
    Put RDP in its own application segment (host + 3389 only) instead of adding the port to the general web segment, and attach an access policy scoped to an admin group, ideally with posture or device-trust criteria. Consider Privileged Remote Access (clientless, recorded sessions) for third parties. Then a regular intranet user still gets only the website, and admin access is separate, auditable and easy to revoke.
Task 13.1 Verify Access to the Internal Application Using RDP ▾

In this task, you add the RDP port to the Intranet segment, connect with Remote Desktop through ZPA, and find the session in the logs.

1 Enable the RDP port in the Application Segment

  1. On the Corp Client PC, open a web browser and go to the Experience Center. Type Application Segments in the Search menu and select the result (Private Access > Private Applications).
  2. Find the Intranet App Segment and click Edit.
  3. In the Edit Application Segment window:
    • Scroll to the port configuration section.
    • Add the RDP port (3389) to the TCP Port Ranges.
  4. Click Save.
Defined Application Segments → Edit (pencil) on Intranet.
Choosing RDP under Default Port Ranges adds 3389 to the TCP (and UDP) ranges next to port 80. Then Save.

2 Connect using Remote Desktop Connection

  1. On the Corp Client PC, open the Remote Desktop Connection application.
  2. Enter the following:
    • Computer: intranet.patraining.safemarch.com
    • Username: student
    • Password: Admin-123!
  3. Confirm that you reach the internal application with the Remote Desktop application.
Open Remote Desktop Connection.
Computer intranet.patraining.safemarch.com, user student, then Connect.
You're on the server's desktop. The connection bar at the top shows intranet.patraining.safemarch.com.

3 Verify the RDP connection and logs

  1. Open Command Prompt and type: netstat -fn
    • Confirm that port 3389 is listed as an ESTABLISHED connection.
  2. Type Applications in the Search menu and click it (Private Access > Dashboards).
  3. Find the entry for intranet.patraining.safemarch.com:3389.
  4. Click the entry to view its Diagnostics.
netstat -fn: an ESTABLISHED session to :3389.
Private Access → Dashboards → Applications: intranet.patraining.safemarch.com:3389 appears under Recent Applications Accessed.
Diagnostics for the session: access policy Allow Intranet, user student, App Connector OnPrem, server :3389.

Note: With Zscaler Private Access (ZPA), you can securely reach a Windows server over Remote Desktop from any internet-connected device running Zscaler Client Connector. Once an administrator has the right entitlement, they can also reach internal applications hosted in the data center.

4 (Optional) Troubleshooting steps

  1. If you have issues establishing the RDP connection, or to see what a block looks like:
    • In the Experience Center, edit the Intranet Application Segment under Application Segments and remove the RDP ports (TCP 3389, UDP 3389) from the TCP and UDP Port Ranges.
    • Try to reconnect with the Remote Desktop Connection app, using the same credentials and connection details as before.
Without 3389 in the segment: "This computer can't connect to the remote computer."

Note: The RDP connection fails because port 3389 is no longer defined in the application segment, so ZPA can't forward the traffic.

5 Validate Diagnostics and Access Policy Blocks

  1. Type Applications in the Search menu and click it (Private Access > Dashboards).
  2. Scroll down to Top Policy Blocks.
  3. Select Access Policy Blocks, then click Show in Logs.
  4. On the Diagnostics page:
    • Expand the log entry for the access attempt.
    • Review the Status Code and the Server IP & Protocol.
Top Policy Blocks → Access Policy Blocks → hover the bar → Show in Logs.
Status code SE: Policy is not configured for access, server :3389. ZPA had no segment covering that port.

Note: The Access Policy Blocks section tracks application requests blocked by access policy rules. Because the RDP port (3389) isn't defined in the App Segment, the user can't reach the internal application, and the error shows up in the diagnostics logs.

🧠
MENTAL NOTE
ZPA app = host + port. Web working ≠ RDP allowed, so add TCP 3389 to the segment. Proof: RDP to intranet.patraining.safemarch.com, netstat -fn ESTABLISHED :3389, Search Applications (Private Access > Dashboards) → the :3389 entry → Diagnostics. Remove the port and the block appears under Top Policy Blocks → Show in Logs as SE: Policy is not configured for access.

QUICK REFERENCE ▲
Student FQDN
Your unique tenant domain, e.g. zs9901.labtenant.com. Used in all login IDs (student@, joe@, bev@).
Experience Center
console.zscaler.com, the unified admin console for ZIA, ZPA, ZDX and the Service Portal. This guide follows the Nav 2.0 layout: open features from the Search menu.
Service Portal
Formerly ZIdentity. The identity layer where users, groups, departments and entitlements are managed and where admins and users authenticate.
ZCC
Zscaler Client Connector, the endpoint agent that tunnels traffic to the Zero Trust Exchange.
Z-Tunnel 2.0
Network-layer tunnel that captures all IP protocols, not just web traffic. Required for Cloud Firewall.
Service Entitlement
Lets a user or group use a Zscaler service (ZIA, ZPA, ZDX) through ZCC.
Admin Entitlement
Lets a user or group administer a service in the console, scoped by a role (e.g. Executive Insights App, ZDX Read-only Admin).
SyncZPA
Additional user attribute (optional value, e.g. 123) that the lab uses to sync the user into ZPA for policy use.
Forwarding Profile
Sets the tunnel type/version and forwarding action for each network context (on-trusted, off-trusted, VPN-trusted).
Cloud App Control
SaaS/Cloud App Policy that allows or blocks individual cloud apps (e.g., allow YouTube). It is enforced ahead of URL category rules.
SSL Inspection
Trusted man-in-the-middle: ZIA decrypts, inspects and re-encrypts traffic using the Zscaler CA. The endpoint must trust the Zscaler Root CA.
Cert Pinning Bypass
A "Do Not Inspect" SSL rule for apps that check the server certificate fingerprint. It must sit above the Inspect All rule.
DLP Engine
Defines what sensitive content looks like (dictionaries + thresholds). Paired with a DLP rule that sets the action.
App Connector
ZPA software in the data center that builds outbound TLS tunnels to the ZPA cloud. No inbound firewall rules needed.
Enrollment Token
OAuth-based one-time code shown on the App Connector console (cat /etc/issue). Entered in App Connectors → Add to enroll the connector into a group.
App Segment
ZPA object that defines a private resource by domain/IP and port. Combined with an access policy, it grants ZPA access.
SIPA
Source IP Anchoring. Sends selected ZIA traffic out through a ZPA App Connector so the destination sees your organization's own egress IP.
ZDX Score
0–100 measure of end-to-end digital experience. Below 50 = Poor, 50–79 = Okay, 80 and above = Good.
Y-Engine (Analyze Score)
ZDX root-cause engine. Click a point on ZDX Score Over Time → Analyze Score to see the ranked factors (Wi-Fi, DNS, latency…) and their confidence.
ZAgent
AI assistant in the Experience Center (top-right icon). With the Digital Experience agent and Troubleshooting skill, it explains the root cause of a user's poor experience.
ZDX Probe
Synthetic test run by ZCC in the background that continuously measures DNS time, TCP connect, server response and page fetch time.
