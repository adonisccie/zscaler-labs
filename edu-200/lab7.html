Lab 7: Configure DNS Security

LAB 7

Scenario: Safemarch wants to protect its users by blocking access to malicious domains and enforcing acceptable use policies that prohibit gambling websites. As a Zscaler administrator, you will configure DNS security controls, enforce these policies, and validate them with the DNS Insight logs.

Objectives: By the end of this lab, you will:

  • Configure an App Profile so that all DNS traffic flows through the Zero Trust Exchange.
  • Create and test a DNS Control Policy that blocks gambling sites while legitimate domains still resolve.
  • Verify the DNS Control Policy enforcement using DNS Insight Logs to confirm that gambling-related DNS requests are being blocked.
Time: ~20 minutes
Tasks: 7.1 – 7.3
💭 THINK FIRST · DNS AS A CONTROL POINT

Almost every connection starts with a DNS lookup. If you can see and control DNS, you can stop many threats before a single TCP packet is sent.

  • Why does the guide add a wildcard * to Domain Inclusion in the App Profile before creating any DNS rule? What would a user be able to do without it?
    Q1 — MODEL ANSWER
    The wildcard tells ZCC to steer every DNS request through the Zero Trust Exchange, whichever resolver the client targets. Without it, a query sent straight to a public resolver such as 8.8.8.8 could leave the PC outside ZIA's DNS inspection. That's exactly the bypass the nslookup www.gambling.com 8.8.8.8 test checks. Steering first, then policy, means there's no "side door".
  • The rule matches Gambling in both Request categories and Response categories. What's the difference, and why might checking only the request name miss something?
    Q2 — MODEL ANSWER
    The request category is based on the domain name being asked for. The response category is based on what the answer resolves to, such as a CNAME target or IP addresses. An innocent-looking or brand-new domain can CNAME or point to infrastructure that is categorized as gambling (or malicious). Checking both sides catches look-alike domains, redirectors and fast-changing hosts that the name alone wouldn't reveal.
  • Lab 6 already blocks the Gambling URL category for web traffic. What extra value does blocking it at the DNS layer add?
    Q3 — MODEL ANSWER
    URL filtering only acts on HTTP/HTTPS requests. A DNS block stops resolution for every protocol: native apps, non-web ports, malware beacons and DNS tunneling. It also acts earlier, before any connection, and gives a separate log source (DNS Insights) for spotting infected hosts querying bad domains. Defense in depth: the same policy enforced at two layers.
Task 7.1 Configure App Profile ▾

In this task, you will update the App Profile to steer all DNS traffic through Zscaler for inspection, so no DNS request bypasses monitoring.

1 Edit the HandsOnLab Windows App Profile

  1. From the Experience Center, go to Infrastructure > Connectors > Client > Platform Settings > Windows.
  2. Click the Edit icon on the HandsOnLab policy.
  3. Under Traffic Steering, click the DNS tab.
  4. In the Domain Inclusion text box, enter the wildcard *
  5. Click Create “*” and Save.
Infrastructure → Connectors → Client → Platform Settings → Windows.
Edit the HandsOnLab policy you created in Lab 3.
Traffic Steering → DNS tab.
Domain Inclusion: type *, choose Create “*”, then Save.

2 Save and update the policy

  1. In Zscaler Client Connector (ZCC) on the Corp Client PC, select More and click Update Policy.
ZCC → More → Update Policy pulls the new DNS steering immediately.
Task 7.2 Configure a DNS Control Policy ▾

In this task, you will create and test a DNS Control rule that blocks gambling domains while allowing legitimate traffic.

1 Test DNS resolution before configuration

  1. Open a command prompt on the Corp Client PC and run: nslookup www.gambling.com

Note: The DNS request resolves successfully because no policy has been configured yet.

Before the rule: www.gambling.com resolves to real addresses.

2 Create a DNS Control Policy

  1. From the Experience Center, go to Policies > Firewall > DNS Control.
  2. Look at the existing predefined DNS Control Rules, which are based on best practice recommendations.
  3. Click Add DNS Filtering Rule.
Policies → Firewall → DNS Control.
Click Add DNS Filtering Rule.

3 Define the rule attributes

  1. Rule Order: 1
  2. Rule Name: Block Gambling
  3. Rule Status: Enabled
Order 1, name Block Gambling, Enabled.

4 Define the DNS Application parameters

  1. Click the DNS Application tab.
  2. Under Request Categories, select Gambling. Click Done.
  3. Under Response Categories, select Gambling. Click Done.
  4. Scroll down. Under Action, set Network Traffic to Block.
  5. Click Save and Activate the changes with the Activation icon (cloud with arrow) in the top-right corner.
DNS Application tab: Request and Response Categories = Gambling.
Action → Network Traffic: Block, then Save.
Activate to push the DNS rule live.

5 Test the new DNS settings

  1. In the Command Prompt window, test: nslookup www.google.com

    Note: Expected result: the DNS request resolves successfully.

  2. Type: ipconfig /flushdns
  3. Type: nslookup www.gambling.com 8.8.8.8

    Note: Expected result: the DNS request times out, which confirms that gambling domains are blocked.

Legitimate domains such as www.google.com still resolve.
Flush the local DNS cache so the next lookup can't use a cached answer.
nslookup www.gambling.com 8.8.8.8 → timed out, even when you point at Google's public resolver.
Task 7.3 View DNS Insight Logs ▾

In this task, you will review the DNS Insight Logs to confirm that the DNS Control Policy is applied and blocking gambling domains as expected.

1 Access the DNS Insight logs

  1. In the Experience Center landing page, go to Logs > Internet & SaaS > DNS Insights > Logs.

2 Configure the log settings

  1. Set the Timeframe to Current Day.
  2. Click Add Filter and add the filter: Rule Name = Block Gambling
  3. Click Run Query.

Note: Allow about 15 minutes for logs to become available. You can move on to the next steps and come back to the log data once it's populated.

DNS Insights → Logs: Timeframe Current Day, filter Rule Name = Block Gambling, Run Query.

3 Verify the Block Gambling activity

  1. Confirm that DNS requests for gambling-related domains show hits on the Block Gambling DNS Control rule and that the action shows blocking.
Each www.gambling.com lookup is logged against Block Gambling with a Block action.
🧠
MENTAL NOTE
Steer, then control. App Profile → DNS → Domain Inclusion * sends every query through Zscaler (then ZCC Update Policy). DNS Control rule Block Gambling matches request and response categories. Proof: google.com resolves, but gambling.com times out even via 8.8.8.8, and DNS Insights shows the hits (allow ~15 min).

Application-layer policy that identifies apps by DPI (e.g., WhatsApp) regardless of port. Separate from Firewall Filtering.

Trusted man-in-the-middle: ZIA decrypts, inspects and re-encrypts traffic using the Zscaler CA. The endpoint must trust the Zscaler Root CA.

A "Do Not Inspect" SSL rule for apps that check the server certificate fingerprint. It must sit above the Inspect All rule.
DLP Engine
Defines what sensitive content looks like (dictionaries + thresholds). Paired with a DLP rule that sets the action.

ZPA object that defines a private resource by domain/IP and port. Combined with an access policy, it grants ZPA access.

ZDX Copilot
AI assistant in ZDX that answers natural-language questions and summarizes root cause for a user's experience issue.
