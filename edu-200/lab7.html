Lab 7: Configure DNS Security

LAB 7

Scenario: Safemarch aims to protect its users by blocking access to malicious domains and enforcing acceptable-use policies that prohibit access to gambling websites. As a Zscaler administrator, you will configure DNS security controls, enforce these policies, and validate them using the DNS Insight logs.

Objectives: By the end of this lab, you will:

  • Configure an App Profile so that all DNS traffic flows through the Zero Trust Exchange.
  • Create and test a DNS Control Policy that blocks gambling sites while legitimate domains still resolve.
  • Verify DNS Control Policy enforcement in the DNS Insight logs, confirming that gambling-related DNS requests are blocked.
Time: ~20 minutes
Tasks: 7.1 – 7.3
💭 THINK FIRST · DNS AS A CONTROL POINT

Almost every connection starts with a DNS lookup. If you can see and control DNS, you can stop many threats before a single TCP packet is sent.

  • Why does the guide add a wildcard * to Domain Inclusion in the App Profile before creating any DNS rule? What would a user be able to do without it?
    Q1 — MODEL ANSWER
    The wildcard tells ZCC to steer every DNS request through the Zero Trust Exchange, whichever resolver the client targets. Without it, a query sent straight to a public resolver such as 8.8.8.8 could leave the PC outside ZIA's DNS inspection. Look at the nslookup output in Task 7.2: the Corp Client PC's resolver is dns.google (8.8.8.8), yet the gambling lookup still times out, because ZCC steered it to Zscaler first. Steering first, then policy, means there's no "side door".
  • The rule matches Gambling in both Request categories and Response categories. What's the difference, and why might checking only the request name miss something?
    Q2 — MODEL ANSWER
    The request category is based on the domain name being asked for. The response category is based on what the answer resolves to, such as a CNAME target or IP addresses. An innocent-looking or brand-new domain can CNAME or point to infrastructure that is categorized as gambling (or malicious). Checking both sides catches look-alike domains, redirectors and fast-changing hosts that the name alone wouldn't reveal.
  • Lab 6 already blocks the Gambling URL category for web traffic. What extra value does blocking it at the DNS layer add?
    Q3 — MODEL ANSWER
    URL filtering only acts on HTTP/HTTPS requests. A DNS block stops resolution for every protocol: native apps, non-web ports, malware beacons and DNS tunneling. It also acts earlier, before any connection, and gives a separate log source (DNS Insights) for spotting infected hosts querying bad domains. Defense in depth: the same policy enforced at two layers.
Task 7.1 Configure App Profile ▾

In this task, you will update the App Profile to steer all DNS traffic through Zscaler for inspection, so no DNS request bypasses monitoring.

1 Edit the HandsOnLab Windows App Profile

  1. On the Experience Center home page, type Windows in the Search menu and select the result (Infrastructure > Client Connector > App Profile & Platform Settings).
  2. Click the Edit icon for the HandsOnLab policy.
  3. Under Traffic Steering, click the DNS tab.
  4. In the Domain Inclusion text box, enter the wildcard *
  5. Click Create “*”, then Save.
App Profiles → Windows: click the Edit (pencil) icon on HandsOnLab, the policy you created in Lab 3.
Traffic Steering → DNS tab.
Domain Inclusion: type *, choose Create “*”, then Save.

2 Update the policy on the client

  1. Open Zscaler Client Connector on the Corp Client PC, select More and click Update Policy.
ZCC → More → Update Policy pulls the new DNS steering immediately.
Task 7.2 Configure a DNS Control Policy ▾

In this task, you will create and test a DNS Control rule that blocks gambling domains while allowing legitimate traffic.

1 Test DNS resolution before configuration

  1. Open a command prompt on the Corp Client PC and run: nslookup www.gambling.com
Before the rule: www.gambling.com resolves to real addresses.

Note: The DNS request resolves successfully because no policy has been configured yet.

2 Create a DNS Control Policy

  1. On the Experience Center home page, type DNS Control in the search bar and select the result (Internet Access > Policy).
  2. View the existing predefined DNS Control rules, which are based on best-practice recommendations.
  3. Click Add Rule.
The predefined rules already block critical- and high-risk DNS categories and tunnels. Gambling isn't a risk category, so it needs its own rule.
Click Add Rule (top right).

3 Define the rule attributes

  1. Under Actions, set Network Traffic to Block.
  2. Rule Name: Block Gambling
  3. Rule Order: 1
  4. Rule Status: Enabled

4 Define the criteria

  1. Click Add Criteria and select the following options:
    • Under Request Categories, select Gambling. Click Done.
    • Under Response Categories, select Gambling. Click Done.
  2. Click Save, then Activate the changes from the Activation icon (cloud with arrow) in the top-right corner.
Criteria → DNS Application: Request Categories and Response Categories = Gambling. Actions: Network Traffic Block. Name Block Gambling, order 1.

5 Test the new DNS settings

  1. In the Command Prompt window, run: nslookup www.google.com. Expected result: the request resolves successfully.
  2. Run: ipconfig /flushdns
  3. Run: nslookup www.gambling.com. Expected result: the request times out, confirming that gambling domains are blocked.
Legitimate domains such as www.google.com still resolve.
Flush the local DNS cache so the next lookup can't use a cached answer.
www.gambling.com now times out, even though the PC asks dns.google (8.8.8.8): ZCC steers the query to Zscaler, which blocks it.
Task 7.3 View DNS Insight Logs ▾

In this task, you will confirm that the DNS Control Policy is applied and blocking gambling domains by reviewing the DNS Insight logs.

1 Open DNS Insights

  1. On the Experience Center home page, type DNS Insights in the search bar and select the result (Data Explorer > Internet & SaaS).

2 Configure the log settings

  1. Set the Timeframe to Current Day.
  2. Click Add Filter and add the filter Rule Name: Block Gambling
  3. Click Run Query.
DNS Insights → Logs: Timeframe Current Day, filter Rule Name = Block Gambling, then Run Query.

Note: Allow about 15 minutes for logs to become available. You can continue with the next steps and come back to the log data once it's populated.

3 Verify the Block Gambling activity

  1. Confirm that DNS requests for gambling-related domains show hits on the Block Gambling DNS Control rule and that the action shows blocking behavior.
Each www.gambling.com lookup is logged for the student user with category Gambling and action Block.

Student FQDN
Your unique tenant domain, e.g. zs9901.labtenant.com. Used in all login IDs (student@, joe@, bev@).
Experience Center
console.zscaler.com, the unified admin console for ZIA, ZPA, ZDX and the Service Portal. This guide follows the Nav 2.0 layout: open features from the Search menu.
Service Portal
Formerly ZIdentity. The identity layer where users, groups, departments and entitlements are managed and where admins and users authenticate.
ZCC
Zscaler Client Connector, the endpoint agent that tunnels traffic to the Zero Trust Exchange.
Z-Tunnel 2.0
Network-layer tunnel that captures all IP protocols, not just web traffic. Required for Cloud Firewall.
Service Entitlement
Lets a user or group use a Zscaler service (ZIA, ZPA, ZDX) through ZCC.
Admin Entitlement
Lets a user or group administer a service in the console, scoped by a role (e.g. Executive Insights App, ZDX Read-only Admin).
SyncZPA
Additional user attribute (optional value, e.g. 123) that the lab uses to sync the user into ZPA for policy use.
Forwarding Profile
Sets the tunnel type/version and forwarding action for each network context (on-trusted, off-trusted, VPN-trusted).
Cloud App Control
SaaS/Cloud App Policy that allows or blocks individual cloud apps (e.g., allow YouTube). It is enforced ahead of URL category rules.
SSL Inspection
Trusted man-in-the-middle: ZIA decrypts, inspects and re-encrypts traffic using the Zscaler CA. The endpoint must trust the Zscaler Root CA.
Cert Pinning Bypass
A "Do Not Inspect" SSL rule for apps that check the server certificate fingerprint. It must sit above the Inspect All rule.
DLP Engine
Defines what sensitive content looks like (dictionaries + thresholds). Paired with a DLP rule that sets the action.
App Connector
ZPA software in the data center that builds outbound TLS tunnels to the ZPA cloud. No inbound firewall rules needed.
Enrollment Token
OAuth-based one-time code shown on the App Connector console (cat /etc/issue). Entered in App Connectors → Add to enroll the connector into a group.
App Segment
ZPA object that defines a private resource by domain/IP and port. Combined with an access policy, it grants ZPA access.
SIPA
Source IP Anchoring. Sends selected ZIA traffic out through a ZPA App Connector so the destination sees your organization's own egress IP.
ZDX Score
0–100 measure of end-to-end digital experience. Below 50 = Poor, 50–79 = Okay, 80 and above = Good.
Y-Engine (Analyze Score)
ZDX root-cause engine. Click a point on ZDX Score Over Time → Analyze Score to see the ranked factors (Wi-Fi, DNS, latency…) and their confidence.
ZAgent
AI assistant in the Experience Center (top-right icon). With the Digital Experience agent and Troubleshooting skill, it explains the root cause of a user's poor experience.
ZDX Probe
Synthetic test run by ZCC in the background that continuously measures DNS time, TCP connect, server response and page fetch time.
