Lab 2: Review Enforced Policies and Explain Outcomes (AI Guard)

LAB 2

Scenario: With the AI landscape mapped in AI Protect, you now shift from visibility to enforcement. In Lab 1, you found where AI is used and how its resources are exposed. This lab covers how AI Guard inspects that usage in real time. Use AI Guard to review transaction events, confidence scores, Detector outcomes, and policy configuration — then collect evidence to hand off to auditors and risk owners showing how these controls map to the governance and compliance requirements that apply to your organization.

  • Navigate AI Guard dashboard views for applications and users
  • Inspect transaction details including Detector confidence and model usage
  • Interpret Governance & Compliance mappings and relate them to AI Guard configurations and events
Time: ~20 minutes

Note: In this lab, you track specific transactions, Detectors, and HIPAA citations across multiple tasks. Use any note-taking method you prefer — the ASK A QUESTION / ADD A NOTE boxes at the bottom of each task work well for this.

💭 THINK FIRST · READING ENFORCEMENT DECISIONS

AI Guard doesn't just say "allowed" or "blocked" — it says so separately for the prompt and the response, and it ties every decision back to a named Detector. Before you start reading transactions, think about what that separation buys you.

  • A transaction can show Prompt Action = Allowed and Response Action = Blocked. What does that combination tell you about where AI Guard is applying judgment?
    Q1 — MODEL ANSWER
    It means the input passed inspection on its own — nothing suspicious in what the user asked — but the LLM's output triggered a Detector, e.g. the response leaked PII, code, or secrets that weren't visible in the prompt. This is exactly the intern's mistake pattern: an innocuous-looking request can still generate a response worth blocking.
  • The same Detector (e.g. Secrets or PII) can appear under multiple HIPAA citations at once. Why doesn't that make the compliance mapping redundant?
    Q2 — MODEL ANSWER
    A single control can satisfy several regulatory obligations simultaneously — that's the point of enforcing it. Secrets detection serves both the "Security Management Process: Risk analysis" safeguard (finding the exposure) and "Access Control" (preventing unauthorized use of leaked credentials). One Detector, multiple compliance justifications — exactly what you'd tell an auditor.
  • Why does this lab ask you to connect a Detector across three places — a live transaction, a Configuration, and the HIPAA Coverage page — instead of just showing you the compliance mapping directly?
    Q3 — MODEL ANSWER
    Because compliance mappings on paper mean nothing if they're not actually enforced. Confirming the same Detector name appears in a real blocked transaction AND in the active Configuration AND in the regulation mapping is what proves the control is live, not just documented — the difference between "we have a HIPAA policy" and "we can prove HIPAA policy fired."

Start at the AI Guard dashboard to see how AI activity appears as transactions for both applications and users. This connects the intern's prompt and similar activity to concrete events and policy decisions.

  • Open the Zidentity dashboard: in a browser, go to https://sdc.zslogin.net/portal.
  • Select the Zguard icon to open AI Guard.
Open AI Guard from the Zidentity dashboard via the Zguard tile.
  • On the AI Guard dashboard, verify that the AI Applications tab is selected.
  • Observe the aggregates at the top: number of Apps, LLMs, Detections, and Transactions. These summary statistics help you understand AI application usage in your environment at a glance.
The AI Applications table: each row is one transaction, with separate Prompt Action and Response Action outcomes plus which Detectors fired.
  • Select Today to expand the date range filter, then select Last 30 Days to see a broader set of transactions.
  • In the application table, select the View Details icon in the Details column of a transaction.

Note: If no transactions are displayed for the current day, expand the date range filter to a longer search window.

  • Review the list of transactions for that application:
    • Find at least one transaction where Prompt Actions and Response Actions are both Allowed
    • Find at least one transaction where Prompt Actions is Allowed and Response Actions is Blocked

Building on what you saw in Task 2.1, focus on a single user transaction. Trace exactly how AI Guard evaluated one prompt and its response so you can explain the decision to stakeholders.

  • Go to Dashboard in AI Guard, then select the Users tab.
  • Select Today to expand the date range filter, then select Last 30 Days so you can see a broader set of transactions.
Switch from AI Applications to the Users tab to see transactions grouped by user identity instead of app.
  • In the Users table, select View Details (the eye icon) in the Details column of a transaction.
The Users table: 8 transactions across 2 users, with Prompt/Response Detections and Actions per row — click the eye icon to open one.
  • Review the list of recent transactions for that user, including: Overview, Detection Summary, Performance & Network Stats, and Prompt Details (Prompt and Response).
  • In the Overview section of the transaction detail, review:
    • Timestamp and user identity
    • Policy name and severity
    • LLM provider and user agent
    • Prompt Action and Response Action outcomes
  • Review the Detection Summary and identify:
    • Which Detectors triggered (for example, Prompt Injection, PII, Secrets, Toxicity, MaliciousURL, Gibberish, Invisible Text)
    • The result for each Detector — Allowed, Detected, or Blocked
  • Open the Prompt Details section to read the prompt that was evaluated. Relate the content of the prompt back to the Detectors that triggered and the actions that were taken.
  • If available, open the Response Details section to view the LLM response that was evaluated. Consider how the response content relates to the Detector outcomes and policy actions.

Verify: You can explain how AI Guard evaluated application and user transactions, including which Detectors triggered, what actions were taken on the prompt and response, and how to use these tables to correlate application- and user-related event data.

Now that you understand how individual transactions and Detectors behave, shift to the governance view. See how the same Detectors you observed in transactions are mapped to HIPAA safeguards so you can speak to compliance requirements.

  • Go to Security > Policies > Compliance & Regulation from the AI Guard dashboard.
The Compliance & Regulation page covers three frameworks: HIPAA, the EU AI Act, and the NIST AI Framework.
  • Locate the HIPAA Coverage section and expand 45 CFR § 164.306 – Security standards: General rules.
  • Review the Detector column and note three Detectors to use in later tasks — for example, Gibberish, Secrets, PII, Prompt Injection, Toxicity, Invisible Text, or Malicious URL.
  • Read the Summary for each Detector you selected and record:
    • What type of input or behavior it is designed to detect
    • How that detection helps protect electronic protected health information (ePHI) from threats or impermissible uses or disclosures
  • Expand another HIPAA citation, such as Administrative safeguards: Security Management Process: Risk analysis, Risk management, or Technical safeguards: Access Control.
  • Identify at least one Detector that appears in both sections — for example, Secrets, PII, Toxicity, Prompt Injection, or MaliciousURL. Record and compare the Summary text for each.

Verify: You have opened the HIPAA Coverage section, reviewed Detector mappings under 45 CFR § 164.306 and at least one additional HIPAA citation, and identified how Detectors such as Gibberish, Secrets, PII, Prompt Injection, Toxicity, Invisible Text, and MaliciousURL support different HIPAA safeguards. You understand that the same Detector can contribute to several HIPAA requirements depending on the control context.

Connect everything you have seen — transactions, Detectors, and HIPAA mappings — to a specific AI Guard configuration. Interpret how the configured Detectors support HIPAA safeguards without making changes to the tenant.

  • Go to Security > Policies > Configurations.
Three configurations: Zscaler GenAI User Inspection (id 1168) has the broadest Detector set and 7 controls.
  • Select the View Details icon in the Action column of the Configurations table.
  • Review the Configuration Details, including Name and Description.
  • In the Controls section, identify the number of policy controls associated with this configuration. Multiple controls exist in each policy.
  • Review the Prompt Detectors section and look for Detectors that also appear in HIPAA Coverage from Task 2.3, such as Gibberish, Secrets, PII / Personal Data, Prompt Injection, or Toxicity.
  • Review the Response Detectors area (if present) and note any overlap with HIPAA Coverage from Task 2.3, such as MaliciousURL / Malicious URL, URL Reachability, Invisible Text, or Code.
  • Identify two Prompt Detectors that appear in both the Zscaler Gen AI User Inspection configuration and HIPAA Coverage from Task 2.3 — for example, Secrets, MaliciousURL, Prompt Injection, PII, Toxicity.
  • Go to Security > Policies > Compliance & Regulation and expand HIPAA Coverage > 45 CFR § 164.306 – Security standards: General rules. Use the notes you captured in Task 2.3 to confirm how these Detectors support HIPAA safeguards.
The Gibberish and Secrets Detector summaries under 45 CFR § 164.306 — both map back to protecting ePHI from adversarial prompts and credential exposure.
  • Refer back to the transaction you analyzed in Task 2.2 and identify one Detector that:
    • Triggered in that transaction's Detection Summary, and
    • Is enabled in this configuration and appears in HIPAA Coverage
    Use the Detector you noted earlier, if possible, so you can follow a single Detector across the event, configuration, and HIPAA safeguard.
  • Identify how that single Detector connects the event, the configuration, and the HIPAA safeguard. Use your notes from the earlier tasks to explain this connection clearly to an auditor or risk owner.

Verify: You have opened a relevant AI Guard configuration, reviewed its Prompt Detectors and Response Detectors, and confirmed that several Detectors (such as Secrets, PII, Prompt Injection, Toxicity, Gibberish, Invisible Text, and MaliciousURL) match those mapped under HIPAA Coverage. You can explain how the configuration's Detector set supports HIPAA safeguards and how a Detector you observed in a real transaction connects event behavior back to compliance requirements.

🧠
MENTAL NOTE
AI Guard = enforcement. Every transaction has a separate Prompt Action and Response Action — they can differ. Detectors (PII, Secrets, Toxicity, Prompt Injection, Gibberish, Invisible Text, MaliciousURL) drive both, and the same Detector can map to multiple HIPAA/EU AI Act/NIST citations. Trace one Detector across a live transaction → its Configuration → its Compliance mapping to prove a control is actually enforced, not just documented.
