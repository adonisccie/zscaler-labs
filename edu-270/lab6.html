Lab 6: Automating ZPA Application Segments and Policies with the ZPA Terraform Provider

LAB 6

Scenario: In this lab, you use the Zscaler ZPA Terraform provider to automate the deployment of ZPA resources. You create the core ZPA objects, review how they relate to one another in the standard composition flow, and then verify the resulting access policy rules in the Experience Center.

Lab overview objective: Create multiple ZPA resources, including an App Connector Group, a server group, a segment group, eight application segments, and eight corresponding access policies. This lab demonstrates the standard ZPA composition flow: App Connector Group → Server Group → Segment Group → Application Segment → Access Policy Rule.

  • Create ZPA resources by using the Zscaler ZPA Terraform provider
  • Review the standard ZPA composition flow across related resources
  • Apply a Terraform plan to deploy application segments and access policies
  • Verify created ZPA resources and policy rules in the Experience Center
  • Remove deployed resources by using Terraform
Time: ~30 minutes
Tools: VS Code, Terraform, zscaler/zpa provider
Task 6.1 Deploy ZPA Resources with Terraform ▾

In this task, you review the Terraform files, initialize the provider, plan the deployment, apply the configuration, and verify the created resources.

1 Open the lab environment

  1. Go to the Corp: Client PC and open File Explorer > Local Disk (C:).
  2. Open the Labs folder and select the Labs 5-6 folder.
  3. Right-click the ZPA folder and choose Open with Code.

Note: On a Mac, use a secondary click (two-finger click).

Open the ZPA Terraform project from Labs 5-6.

2 Explore the resources in the environment

  1. Open main.tf — notice that all resources are defined in a single Terraform file.
  2. Open versions.tf — notice it references ZPA instead of ZIA; initializing Terraform pulls the ZPA provider.
  3. Open variables.tf — notice it defines the enrollment certificate and rule order.
  4. Open locals.tf — notice it uses an external JSON file to pull in data, separating data from resource definitions.
  5. Click on the data file to review it — it defines the App Connector Group, application segments, access policies, segment group, and server group.
main.tf holds every resource definition — the loop over the JSON data is what generates eight of each.
versions.tf pulls the ZPA provider instead of ZIA — same provider framework, different service.
variables.tf defines shared inputs like the enrollment certificate and rule order.
locals.tf loads the JSON file that supplies all eight segments' and policies' data.
The JSON data file — one entry per application segment and access policy, plus the shared groups.

3 Review the resource relationships

  1. Note that associations between resources are defined by calling referenced ID sequences in the JSON file.
Referenced ID sequences link each access policy to its matching application segment across all eight pairs.
The resource block in main.tf reads these sequences to wire dependencies correctly for every generated instance.

4 Configure the environment variables

  1. Open a new terminal.
  2. Provide the following details, using the credentials from your lab access email:
    • $Env:ZSCALER_CLIENT_ID= <Client ID>
    • $Env:ZSCALER_CLIENT_SECRET= <Client Secret>
    • $Env:ZSCALER_VANITY_DOMAIN= <Vanity Domain>
    • $Env:ZPA_CUSTOMER_ID= <ZPA Customer ID>

Note: In this lab, you must enter these values exactly as shown because Terraform uses them to automate the process.

Open a fresh terminal for the four ZPA environment variables.
ZPA Terraform needs all four variables — the same three as ZIA, plus ZPA_CUSTOMER_ID.

5 Initialize Terraform

  1. Run terraform init to initialize the environment and download the ZPA provider.
terraform init downloads the ZPA provider for this project.

6 Review the planned changes

  1. Run terraform plan -out=tfplan to generate the execution plan.
  2. Review the listed resource changes.
The plan lists all 19 resources — 1 connector group, 1 server group, 1 segment group, 8 application segments, 8 access policies.

7 Apply the Terraform plan

  1. Run terraform apply tfplan to create all defined resources.
One apply, nineteen resources — the composition flow deployed at scale.
Task 6.2 Verify and Remove Deployed ZPA Resources ▾

In this task, you verify the deployed resources in the Experience Center and then remove them by using Terraform.

1 Verify the deployed resources

  1. Go to the Experience Center, navigate to Policies > Private Applications > Access Policy.
  2. Review the eight access policy rules.
  3. Open App Segments and verify that eight application segments were created.
  4. Open Segment Groups and Server Groups and review the created resources.
  5. Verify the App Connector Group creation — navigate to Infrastructure > Private Access > App Connector Groups.
Eight access policy rules — one per application segment, all created by a single apply.
Eight application segments confirm the JSON-driven loop generated every entry correctly.
A single shared segment group groups all eight application segments together.
A single shared server group, referencing the App Connector Group, backs all eight segments.
The App Connector Group appears under Infrastructure → Private Access — the root of the whole composition chain.

2 Remove the deployed resources

  1. Return to the terminal in the lab environment.
  2. Run terraform destroy.
  3. When prompted, enter yes to confirm.
terraform destroy prompts once before removing all 19 resources it created.
Destroy walks the dependency graph in reverse — policies and segments first, shared groups last.

3 Confirm resource deletion

  1. Return to the Experience Center, navigate to Policies > Private Applications > Access Policy.
  2. Verify that the resources created by Terraform have been deleted.

Verify: Confirm that the App Connector Group, server group, segment group, eight application segments, and eight access policy rules were created successfully — and then confirm those resources no longer appear in the Experience Center after the Terraform destroy operation.

The Access Policy list is clean again — every Terraform-managed resource from this lab is gone.
