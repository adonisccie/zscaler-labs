LAB 8 · ZDX

ZDX Alerts & Diagnostics

Monitoring collects data, but without alerting you still rely on users to report problems. In this lab you configure a ZDX alert rule that fires when application performance degrades beyond a threshold, and you launch a Diagnostics Session to capture real-time device telemetry, including Wi-Fi, DNS, cloud path and application metrics, for a specific user.

Lab 8: ZDX Alerts & Diagnostics

LAB 8

Scenario: You are a Network Operations Center (NOC) engineer seeing a spike in complaints that an internal application intermittently freezes or takes too long to load for remote users. By the time IT investigates, performance often returns to normal, which makes it hard to prove impact, identify patterns, and tell whether the issue is user-specific, site-specific, ISP-related or application-related. To reduce mean time to detect (MTTD) and speed up troubleshooting, you configure Zscaler Digital Experience (ZDX) alerts that notify the NOC automatically when user experience degrades beyond acceptable thresholds. When alerts trigger, you launch ZDX Diagnostics Sessions to capture real-time client and network telemetry and pinpoint the likely root cause.

  • Configure ZDX alerting in your Experience Center tenant to detect user-experience degradation (for example, Page Fetch Time or ZDX Score) for a business-critical application.
  • Validate that the alert rule and the ZDX Diagnostics Session report give actionable evidence for NOC troubleshooting and escalation: device resource health (CPU/memory), Wi-Fi signal and local network details, DNS resolution performance, and an application performance breakdown.
Time: ~15 minutes
Service: Zscaler Digital Experience (ZDX)
Prerequisite: Lab 7 probes (Mail Server_Web, Mail Server_Cloud) created and enabled
Task 8.1 Create an Alert Rule ▾

In this task, you add a new alert rule for an application.

  1. On Corp Client PC 1, sign in to Zscaler Client Connector with the student credentials provided to you.
  2. In the Experience Center home page, type Alerts Overview in the Search menu and select the matching option (Digital Experience > Alerts).
    1. Select Alert Rules and Templates to go to the Rules page.
      Alerts Overview › Alert Rules and Templates.
  3. Select Add Alert Rule.
  4. In the Add Alert Rule window, enter:
    • Name: alert_mailserver
    • Status: Enabled
    • Type: Application
    • Severity: Medium
    Configure Rule: alert_mailserver, Enabled, Applications, Medium.
  5. Select Next.
  6. On the Filters tab, configure the application filters, then select Next:
    1. Select the application you created in the previous lab (Mail Server).
    2. Select the probe for the application from the drop-down list (Mail Server_Web).
    Filters: Mail Server and its Web probe.
  7. Add a geolocation filter, then select Next:
    1. Select Add Filter.
    2. Select Geolocation.
    3. Expand the geolocation Asia and select a specific region, for example India.
    Geolocation filter: Asia › India.
  8. On the Criteria tab, create the following criteria, then select Next:
    • Page Fetch Time > 800 ms
    • ZDX Score < 50
    Both conditions must match (ALL): slow page fetch and a poor ZDX Score.
  9. On the Actions tab, enter the following details, then select Next:
    • Alert Only if Repeated: 2 times in a row
    • Number of Active Devices is: 1
    • Alert Delivery Method: Email
    • Alert Recipients: any dummy email ID
    Throttle to 2 repeats on 1 device; deliver by email.
  10. On the Review tab, review the entire configuration and select Save.
    Review, then Save.
  11. Verify that the alert_mailserver alert rule appears in the alert rules list.
    alert_mailserver is enabled.

Task 8.2 Configure a Diagnostic Session ▾

In this task, you create a Diagnostics Session for your organisation's Student user.

  1. In the Experience Center home page, type Diagnostics in the Search menu and select the matching option (Digital Experience > Reports).
    1. Select Start New Diagnostics Session.
      Diagnostics › Start New Diagnostics Session.
  2. If you don't see Start New Diagnostics Session, enable machine hostname collection:
    1. Type User Privacy in the Search menu and select the matching option (Infrastructure > Advanced Settings).
    2. Select the User Privacy tab.
    3. Enable Collect Machine Hostname Information.
    4. Select Save.
    5. Refresh the page, then return to Diagnostics and confirm that Start New Diagnostics Session is available.
      Advanced Settings › User Privacy › Collect Machine Hostname Information.
  3. In the Start New Diagnostics Session window, enter:
    • Name: diagnostics_session_student<studentID> (for example, diagnostics_session_student000205)
    • User: the Student Admin user name assigned to you
    • Device: select the user's device
    • Select Deep Tracing and set Run Session For to 5 Minutes
    General: name, user, device, Deep Tracing for 5 minutes.
  4. Select Next.
  5. Select the probes for the session:
    1. Application: Mail Server
    2. Select the Web probe (Mail Server_Web) and the Cloud Path probe (Mail Server_Cloud).
  6. Under Cloud Path Probe Thresholds, set:
    • Packet Loss: 20%
    • Latency: 10 ms
  7. Select Save.
    Probes and Cloud Path thresholds (20% loss, 10 ms), then Save.
  8. In the In Progress table, find the session you just created.
    The session is running (In Progress).
  9. Proceed to the next lab. After five minutes, return to Diagnostics:
    1. In the History table, locate the completed session.
      The completed session in History.
    2. Select the View icon to open the session report.
      The session report: hop-by-hop Cloud Path and latency over the session.

QUICK REFERENCE ▲
Experience Center
console.zscaler.com, the unified admin console for ZIA, ZPA, ZDX and the Service Portal. This guide uses the new navigation: open features from the Search menu.
Search menu
The search box in the Experience Center top bar. Type a feature name (e.g. App Connector Groups) and pick the result; each result shows its menu path.
Service Portal
Formerly ZIdentity. Zscaler's authentication service, reached from the Experience Center menu.
Student FQDN
Your pod's unique domain (e.g. zs000834.labtenant.com). Used in every login ID: student@, hvac@.
CloudShare
The virtual lab platform that hosts your VMs. Use Actions › Send Text or Send Password to paste into a VM.
App Connector
A lightweight VM in the data center that makes outbound-only connections to ZPA, so private apps are reachable without inbound firewall ports.
App Connector Group
A set of App Connectors that share a location and settings. Server groups point to it.
Enrollment token
The OAuth code shown by cat /etc/issue on a connector. Add it under App Connectors to enroll the connector; it expires after two hours.
Application Segment
Defines a private app (domain or IP plus ports) and how it is reached: Client Connector, Browser Access or Privileged Remote Access.
Segment / Server Group
A segment group bundles segments for policy; a server group maps segments to App Connector groups.
Browser Access
Clientless ZPA access to a web app through its External Domain, with no Client Connector or VPN.
Access Policy
ZPA rules, default deny, that allow access to segments when criteria such as Applications and Client Types match.
Log Streaming Service (LSS)
Streams ZPA logs (e.g. User Activity) through an App Connector to a syslog receiver such as a SIEM.
Log Receiver
The LSS destination: host, TCP port, App Connector group, log type and template (e.g. CSV).
Privileged Remote Access (PRA)
Clientless, browser-based RDP and SSH to servers through a privileged portal, with session recording and credential vaulting.
Privileged Portal / Console
The portal is the web page users open; each console on it is one server (protocol, host, port).
Privileged Credentials
Vaulted usernames and passwords that a credentials policy injects into a console, so users never see them.
AppProtection
Inline web-application firewall in ZPA: OWASP CRS, ThreatLabZ, WebSocket and API controls on private app traffic.
Paranoia level
How wide a net the OWASP controls cast: higher levels catch more but raise false positives.
Isolation Profile
Settings for Browser Isolation of private apps, e.g. render-only with View Office Files in Isolation.
End User Collection
A ZDX container that sets which users and devices run the probes of the applications inside it.
Web / Cloud Path probe
A Web probe times page fetches to a URL; a Cloud Path probe traces hop-by-hop latency, loss and jitter to the host.
SDC
Solutions Demo Center: a shared, read-only tenant with pre-populated data, used for the reporting and Workflow Automation labs.
