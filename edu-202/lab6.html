LAB 6 · ZPA

ZPA AppProtection

AppProtection embeds a web application firewall into ZPA's data path, inspecting every private application request against OWASP CRS rules, ThreatLabZ intelligence, and protocol-specific controls. In this lab you protect the Damn Vulnerable Web App (DVWA) — deliberately insecure — and watch SQL injection and XSS attacks flow through in Report mode before switching to Block.

Lab 6: ZPA AppProtection

LAB 6

Scenario: You are a security engineer responsible for protecting internal web applications from common vulnerabilities such as SQL injection and cross-site scripting (XSS). You configure Zscaler Private Access™ (ZPA) AppProtection to inspect traffic and enforce security controls for the Damn Vulnerable Web App (DVWA).

Time: ~30 minutes
Service: Zscaler Private Access (ZPA) — AppProtection
Prerequisite: App Connector running and connected
Task 6.1 Creating Application Segment ▾

In this task, you create the DVWA application segment, define the necessary access policy, and add the DNS entry that lets the App Connector resolve the DVWA hostname.

  1. On the Corp Client PC 1, open the Experience Center portal.
  2. Go to Policies > Access Control > Private Applications > Defined Application Segments.
  3. Select Add Application Segment.
  4. Configure the application segment.
    1. Enter the following values:
      • Name: DVWA
      • Applications: dvwa-<XYZ>.patraining.safemarch.com (XYZ is the last 3 digits of the tenant assigned to you. For example, if your tenant is ZS000205, the application name is dvwa-205.patraining.safemarch.com)
      • Access Type: Browser Access and App Protection
      • Certificate Type: Managed
      • Under External URL: Domain Prefix dvwa; Domain Suffix: select any one from the drop-down
      • Under Internal URL: Protocol HTTP; Port 80
      • Under Client Connector Access: Default Port Ranges Web Server
      Select Next.
    2. Select the segment group: Name CorpApps, Status Enabled. Select Next.
    3. Select the server group: Name CorpServers. Select Next.
    4. Review and save the configuration.
  5. Verify the settings and select Save.
  6. After you save, in the Add Application Segment window, select Edit Policy to verify the addition. Alternatively, go to Policies > Access Policy.
  7. Create the access policy rule. Select Add and configure the following:
    • Rule Name: dvwa_allow_policy
    • Rule Action: Allow Access
    • Criteria: select Applications and choose the DVWA application segment
    Select Save.
  8. In the Corp Win Svr 2025 VM, open Server Manager, select Tools at the top-right corner, and select DNS to open the DNS Manager.
  9. In the left panel of DNS Manager, locate the entry for host-1.patraining.safemarch.com. Expand the forward lookup zone to find patraining.safemarch.com. Right-click the entry and select New Host (A or AAAA).
  10. In the New Host window, enter:
    • Name: dvwa-XYZ (XYZ is the last 3 digits of the tenant assigned to you)
    • Fully Qualified Domain Name (FQDN): populated automatically from the name you provide
    • IP address: 10.0.0.128
  11. Click Add Host to add the entry.
  12. Verify that the entry was added successfully.

Note: The DVWA application runs in a Docker container (10.0.0.128), so you add a DNS entry that redirects the traffic to the container hosting DVWA. After you add the DNS entry on the Corp Win Svr 2025 VM, it can take 3–5 minutes for the change to take effect.

Task 6.2 Set Up AppProtection Profiles ▾

In this task, you create a profile for reporting. A Protection Profile defines which control groups are active and at what enforcement level.

  1. Create the reporting profile.
    1. In the Experience Center console, go to Policies > Cybersecurity > Inline Security > Private App Protection > Protection Profiles.
    2. On the App Protection tab, select Add (+).
    3. Configure the profile: Name DVWA_Protection_Profile; Description optional.
      Select Next.
    4. On the Controls tab, select OWASP_CRS/4.8.0 from the OWASP Predefined Control drop-down, and select all the OWASP predefined controls.
    5. Similarly, on the ThreatLabZ Controls, WebSocket Controls, API Controls, and Active Directory Controls tabs, select all controls.
    6. Select Next.
    7. Set the Predefined Paranoia Level to 3, then select Next.
    8. Configure the Override Controls: set Alternate Action to Override All Controls, and set Transaction to Allow for the OWASP Predefined Controls, WebSocket Controls, ThreatLabZ Controls, API Controls, and Active Directory Controls.
    9. Select Next, then Save.

Note: Higher paranoia levels execute checks using a wide net of matches, which increases the potential for false positives. Lower paranoia levels execute checks using a precise set of matches, which results in fewer false positives.

Task 6.3 Set Up AppProtection Policies ▾

In this task, you apply the protection profile to the DVWA application segment and enable inspection.

  1. In the Experience Center console, go to Policies > Cybersecurity > Inline Security > Protection Policies > AppProtection Policy.
    1. Select Add (+).
    2. Configure the policy:
      • Name: DVWA_AppProtection_policy
      • Description: optional
      • Rule Action: Inspect
      • AppProtection Profile: DVWA_Protection_Profile (created in Task 6.2)
    3. Select Add Criteria, select Applications, and choose the DVWA app segment.
    4. Select Save.

Note: Rule Action: Inspect means ZPA runs traffic through the Protection Profile. The profile's Override Controls (Allow) determine whether matching requests are blocked or merely logged. If you set Rule Action to Bypass, AppProtection is skipped entirely for this traffic.

Task 6.4 Testing & Verification ▾

In this task, you perform sample attacks to verify logging, and then update the protection profile to block those attacks.

  1. Access DVWA through Browser Access.
    1. Log out of Zscaler Client Connector (ZCC).
    2. On Corp Client PC 1, open a browser and sign in to the Experience Center tenant at www.console.zscaler.com by using the credentials provided to you.
    3. Go to Policies > Access Control > Clientless > Access Methods > Browser Access.
    4. Copy the External Domain for the application (internal domain dvwa.patraining.safemarch.com).
    5. Open a new browser window, paste the External Domain, and authenticate by using your lab access credentials.
    6. Sign in to DVWA with Username admin and Password password.
  2. Initialize the DVWA database. Scroll down and select Create / Reset Database. After the reset completes, sign in to DVWA again.
  3. Perform a SQL injection test (expected: allowed and logged). In DVWA, go to SQL Injection, enter 1' or '1'='1 in the User ID field, and select Submit.

Note: The attack is successful because the policy is set to Allow (Report mode).

  1. Perform an XSS (Stored) test (expected: allowed and logged). In DVWA, select XSS (Stored) and enter Name JSAttack and Message <script>alert("You've been HACKED!")</script>, then select Sign Guestbook.
  2. Verify violations in Private Application Diagnostics. In the Experience Center console, go to Logs > Insights > Private Applications > Diagnostics. Set the Log Type to AppProtection, then scroll to Security Profile Violations to view the logged events. Confirm that the Protection Profile allowed the attack to reach the application through ZPA.
  3. Update the protection profile to block, then re-test. Go to Policies > Cybersecurity > Inline Security > Protection Profiles and edit DVWA_Protection_Profile. Set the control action to Block for each control group.
  4. Sign in to DVWA again with Username admin and Password password.
  5. Attempt the SQL injection test again.
  6. Confirm that the application access is now blocked.
  7. Review the logs again. Return to Logs > Insights > Private Applications > Diagnostics, set the Log Type to AppProtection, and scroll to Security Profile Violations to view the logged events.

Note: Earlier, the control action was set to Allow, so attack traffic was permitted through ZPA and logged. After you change the control action to Block, the attacks are blocked and the corresponding events appear in diagnostics.
