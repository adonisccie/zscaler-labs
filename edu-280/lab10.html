Lab 10: Test WAN Link Failover

OPTIONAL LAB

When an internet link fails, the branch carries two kinds of traffic that recover in different ways. Traffic that a Routing Policy (PBR) rule sends direct to the internet already knows both WAN next hops, so it simply moves to the remaining link. Traffic that goes to ZIA travels inside a DTLS tunnel, so the gateway must move it to the tunnel on the other link first. In this lab you take the primary link (GE1) down and compare the two.

Scenario: The primary ISP (GE1) is down for maintenance. The business-critical SaaS application (Adobe, Lab 5) must keep working, and general internet traffic through ZIA must recover on its own.

In this lab you will:

  • Review the HA settings and find the Active unit.
  • Start test traffic to Adobe (PBR) and to 8.8.8.8 (ZIA) and find the link Adobe uses.
  • Turn GE1 off and compare how both pings behave.
  • Prove that Adobe traffic now leaves on GE2, then restore GE1.

Success criteria — tick when done

  • ☐ The ping adobe.com window kept replying while GE1 was off.
  • ☐ tcpdump on ge2 shows the Adobe ICMP packets after the change.
  • ☐ ge1 Admin Status is on for both gateways at the end of the lab.

Watch out for

  • ⚠ Adobe ping stops for a long time — check that the Lab 5 rule pod##-SaaS-Apps-WAN is committed with Traffic Distribution Best and both next hops.
  • ⚠ No Adobe packets on ge1 before the test — Best already chose ge2; capture on ge2. The test still shows that losing GE1 does not affect Adobe.
  • ⚠ gw-02 is the Active unit — normal if a failover happened earlier; run the commands on whichever unit is Active.

💭 THINK FIRST · WAN LINK FAILOVER

Two kinds of traffic cross the branch, and they recover differently.

  • Why does the Adobe ping barely notice GE1 failing?
    Q1 — MODEL ANSWER
    The PBR rule already has both next hops; when ge1 goes down its next hop is removed and Best sends traffic to the remaining link. Nothing has to be rebuilt.
  • Why turn ge1 off on both gateways?
    Q2 — MODEL ANSWER
    ge1 is a tracked interface; turning it off only on the Active unit lowers its weight and the Standby could take over, changing the test from WAN failover to gateway failover.
  • What does show appliance-status prove after the failure?
    Q3 — MODEL ANSWER
    The Active unit did not change, so the site survived the ISP loss with a WAN failover, not a gateway failover.
  • In your site open High-Availability. Enable the Preempt and enable the Track Interface lists for ge1, ge2, ge6, ge7, ge8 for both gateways and then click Save.
In your site open High-Availability. Enable the Preempt and enable the Track Interface lists for ge1, ge2, ge6, ge7, ge8 for both gateways and then…

Why: Each setting controls part of the failover decision. VRRP Group ID identifies the pair — both units must use the same ID. Track Interface lists the interfaces whose health counts towards a unit’s weight: when a tracked interface fails, that unit’s weight drops and a healthier peer can take the Active role. Preempt lets the healthier unit take the Active role automatically instead of waiting for the current Active unit to fail completely. Advertisement Interval is how often the Active unit announces itself on the HA link; the Standby takes over after several missed announcements.

  • Open Troubleshooting > Appliance Admin Console, connect to each gateway tab in turn and run vyos show vrrp.
Open Troubleshooting > Appliance Admin Console, connect to each gateway tab in turn and run vyos show vrrp.
APPLIANCE ADMIN CONSOLE — BOTH GATEWAYS
$vyos show vrrp
EXPECTED
One unit shows State MASTER (Active) and the other BACKUP (Standby). The gateway tabs also show (Active) and (Standby).
Last Transition shows how long ago the role last changed.

What you see: In this screenshot gw-02 is Active. When both units are equally healthy, VRRP keeps the current Active unit rather than moving the role back, so either gateway may be Active in your pod.

Why: You need to know which unit carries the traffic before you break anything. Afterwards you can tell a WAN failover (same Active unit, different link) from a gateway failover (different Active unit).

  • On the Server VM, open a Command Prompt and run ping adobe.com -t. Note the Adobe IP address and leave the ping running.

Why: The Lab 5 Routing Policy rule sends ICMP to Adobe direct to the internet with Traffic Distribution Best, using both next hops (10.120.1.254 on GE1 and 10.130.1.254 on GE2). This ping therefore shows how PBR traffic behaves when one link fails.

On the Active unit, run ping 10.120.1.254 and then ping 10.130.1.254.

Why: These are the next hops of the two ISP links (GE1 and GE2). Proving both answer now means any failure you see later is caused by your test, not by an existing problem.

Caution: Turn ge1 back on for both gateways before you leave this lab. While ge1 is off, the branch has no WAN redundancy.

APPLIANCE ADMIN CONSOLE — ACTIVE UNIT
$tcpdump -i ge1 host <Adobe IP>
EXPECTED
ICMP echo requests from 10.1.10.10 to the Adobe IP on the link that Best selected (usually ge1).

Why: You need to know which link carries Adobe before you break one. Seeing the Adobe IP in clear text on a WAN interface also confirms the traffic leaves direct and not through the ZIA tunnel.

  • In your site open Interfaces and select WAN in the filter. Switch Admin Status of ge1 off for pod##-student-lab-gw-01 and for pod##-student-lab-gw-02.
In your site open Interfaces and select WAN in the filter. Switch Admin Status of ge1 off for pod##-student-lab-gw-01 and for pod##-student-lab-gw-02.

Why: ge1 is a tracked interface (Task 10.1). Turning it off only on the Active unit would lower that unit’s weight, and the Standby — which still has both links — could take over the Active role, moving the LAN gateway as well. Turning ge1 off on both gateways simulates the ISP failing for the whole site and keeps this test about WAN failover only.

  • Watch the ping adobe.com -t window. Replies continue; at most one or two may time out while the gateway detects the failure.

Why: The PBR rule already has both next hops. When ge1 goes down, its next hop is removed and Best sends Adobe traffic to the only remaining link. Nothing has to be rebuilt, so the application barely notices.

EXPECTED
ICMP echo requests from 10.1.10.10 to the Adobe IP now appear on ge2.

What you see: [Screenshot to add: tcpdump on ge2 showing the Adobe ICMP packets]

Why: This is the proof of the failover: the same Adobe traffic that used ge1 now leaves on ge2, still direct and still matched by your PBR rule.

Why: The Active unit did not change: the site survived the ISP loss with a WAN failover, not a gateway failover. The gateway also keeps its own connection to the Zscaler cloud over ge2, so the portal can still manage it.

  • In Interfaces, switch Admin Status of ge1 back on for both gateways.
  • After about a minute, click Refresh. ge1 shows Link Status Up and a link score on both gateways.

What you see: Either ping may drop a reply when traffic moves back to ge1.

Why: Restoring ge1 shows that the link recovers without manual work and puts the branch back on two WAN links for the remaining labs.

  • Stop both Server pings with Ctrl+C.

Note: VRRP priority does not use the WANmon path score. A WAN link connected through a switch can stay Up while the ISP is down, so tracking detects local link failures, not every provider outage.
