Lab 5: Steer SaaS Traffic with Policy-Based Routing

CORE LAB

Policy-based routing (PBR) overrides the default route for selected traffic. Here ICMP to Adobe goes straight out the best WAN link, while everything else still goes through ZIA.

Scenario: The branch uses a SaaS application whose monitoring traffic should go direct to the internet over the best-performing link instead of through the ZIA tunnel.

In this lab you will:

  • Confirm that traffic goes through ZIA before the change.
  • Create a SaaS application object for Adobe.
  • Route ICMP to Adobe direct to WAN with “Best” link selection.
  • Prove the steering with tcpdump and PBR counters.

Success criteria — tick when done

  • ☐ POD##-SaaS Apps object and pod##-SaaS-Apps-WAN rule committed.
  • ☐ tcpdump shows Adobe ICMP on the best WAN link; PBR-RULES counters increase.

Watch out for

  • ⚠ No packets on ge1 — the best link may be ge2 — capture there.
  • ⚠ Adobe IP differs — Akamai addresses change; use the IP from your own ping.

💭 THINK FIRST · SAAS TRAFFIC WITH PBR

Policy-based routing overrides the default path for matching traffic only.

  • Why use a SaaS Application object for Adobe instead of typing IP addresses?
    Q1 — MODEL ANSWER
    Zscaler maintains the SaaS address ranges in the object, so your rule keeps working when Adobe changes addresses.
  • With Traffic Distribution = Best, how does the gateway choose a link?
    Q2 — MODEL ANSWER
    It picks the WAN link with the best score from latency, loss and jitter. If scores are equal it uses the primary WAN of the HA pair with the better overall metrics.
  • How do the tcpdump captures prove which traffic is steered?
    Q3 — MODEL ANSWER
    Adobe ICMP appears in clear text on the best WAN link (ge1 or ge2), so it leaves direct. Non-Adobe traffic such as YouTube shows 0 packets on the WAN and appears on zia0/zia1 instead, so it still goes through the ZIA tunnel.
  • On OT1, browse to http://ip.zscaler.com: traffic goes through Zscaler before the rule.
On OT1, browse to http://ip.zscaler.com: traffic goes through Zscaler before the rule.

APPLIANCE ADMIN CONSOLE — ACTIVE UNIT
$show iptables PBR-RULES -t mangle
EXPECTED
An icmp rule with comment PBR-Policy: pod##-SaaS-Apps-WAN, a MARK value (for example 0x800) and packet counters that grow while the ping runs.
  • Compare with your output.
Compare with your output.

What you see: The match-set numbers identify the source subnet and Adobe destination lists; they differ between pods.

  • Here, the first ICMP-related rule in the PBR-RULES chain shows:
  • Applied Action: The traffic is tagged with MARK set 0x800. (Please note that the specific mark value may vary in your environment.)
  • Protocol: icmp
  • Criteria:
    • Matching source IP in match-set 75 src. (The match-set number 75 is shown as an example and will be different in your lab.)
    • Matching destination IP in match-set 71 dst. (The same applies to this destination IP list.)
    • Direction: ctdir ORIGINAL
    • Policy comment: PBR-Policy: pod01-SaaS-Apps-WAN

This confirms that ICMP traffic from the source subnet matching match-set 75 destined for SaaS apps in match-set 71 is marked and forwarded via the pod01-SaaS-Apps-WAN forwarding policy, with a RETURN rule immediately following to stop further processing once the mark is applied.

MENTAL NOTE
PBR rule = source subnet + SaaS object + port icmp:0 + next hops on ge1/ge2 + Best. Prove it: tcpdump -i ge1 host <Adobe IP> (or ge2) shows it direct; tcpdump -i zia0 shows ZIA traffic; show iptables PBR-RULES -t mangle shows the mark and counters.
