Lab 3: Configure Policy-Based Routing (PBR) Policies

ROUTING

Combining Zero Trust Branch device-level segmentation with ZIA's AI-powered security gives comprehensive Zero Trust protection. In this lab you configure Policy-Based Routing (PBR) to optimise traffic flow: send SaaS application traffic directly out the WAN rather than through the ZIA IPSec tunnels, matching by source subnet and application object.

  • Validate that Internet traffic currently egresses via ZIA (IPSec)
  • Create a SaaS Application object (Adobe) as the PBR destination match
  • Build a PBR rule (icmp:0) that routes matching traffic directly to the WAN
  • Prove the routing with tcpdump and iptables -t mangle

Platform: Skytap + Zscaler Experience Center
  • In Skytap, log into the OT Endpoint Ubuntu Host (VLAN30) and visit ip.zscaler.com. It confirms traffic is currently routed through Zscaler (ZIA) before you add the PBR rule.
Baseline: ip.zscaler.com shows Internet traffic egressing via Zscaler (ZIA IPSec).

Scenario: route ICMP traffic from a source subnet to destinations matching the Adobe SaaS object directly out the WAN (protocol icmp:0), across two gateways in primary/secondary configuration.

PBR scenario — SaaS (Adobe) ICMP routed direct to WAN via gateway definitions.

3.2.1 · Create the SaaS Application object (Adobe)

  • Navigate to Policies [1] › Access Control › Segmentation › Zero Trust Branch › Objects & Groups [2]. Click Add [3], then SAAS Apps [4].
Objects & Groups › Add › SAAS Apps.
  • Rule Name: POD##-SaaS Apps [1]
  • Application name: from the SaaS Apps dropdown, select Adobe [2]
  • Click Add [3] to save the object.
Create the Adobe SaaS object — used as the PBR destination match.

3.2.2 · Configure the PBR routing policy

  • Go to Infrastructure › Connectors › Edge › Zero Trust Branch › Sites and select POD##-Student-Lab.
  • Select Routing Policy [1] › Configure [2], then click Add route.
Open your POD site.
Routing Policy › Configure.
Add route.
  • Rule Name: pod##-SaaS-Apps-WAN [1]
  • Sources: Subnet/Host [2] › 10.1.10.0/24 [3] › Add [4]
  • Destinations: POD##-SaaS Apps [5]
  • Ports: Custom Port [6] › Value icmp:0 [7] › Add [8]
  • Gateway-1: pod##-student-lab-gw-1, Nexthop Type LAN/WAN [9] · Primary ge1(wan) [10] · Secondary ge2(wan) [11]
  • Gateway-2: pod##-student-lab-gw-2, Nexthop Type LAN/WAN [12] · Primary ge1(wan) [13] · Secondary ge2(wan) [14]
  • Traffic Distribution: Best [15] › click Save [16]

Note: Next-hop IPs auto-populate (e.g. 100.120.1.254 for ge1, 100.130.1.254 for ge2). With Distribution = Best, the system picks the WAN interface by performance metrics — latency, loss, jitter.

PBR rule: source 10.1.10.0/24 → Adobe object, icmp:0, dual gateways, Best distribution.
  • Click Commit; the policy takes effect in a few seconds.
Commit — PBR active within seconds.
  • Go to Interfaces [1] › select the WAN [2] interface. Check the best score of the active unit — here the active unit is pod01-student-lab-gw-02 and ge1's best score is 27 [3].

Note: If ge1 and ge2 scores tie, the system uses loss/latency/jitter to choose; if still identical, it may load-balance or follow a tie-break rule.

Interfaces › WAN — best score 27 on ge1 for the active unit.
  • In Skytap, open the Windows Server VM and run ping adobe.com -t. It works as expected; note the resolved IP (e.g. 23.54.127.40).
Open the Windows Server VM.
ping adobe.com -t — note the destination IP for the capture.
  • On the Console of the active unit, capture on each WAN interface (use the best-score interface):
    • tcpdump -ni ge1 -c 5 host 23.54.127.40
    • tcpdump -ni ge2 -c 5 host 23.54.127.40
  • ICMP packets are captured on ge1 (Adobe's IP), while ge2 captures none — the PBR rule routed the traffic direct to WAN.
tcpdump on ge1 captures the Adobe ICMP; ge2 sees nothing.
  • Now validate scoping: ping adobe.com from the OT segment (VLAN30) — stop the Windows Server ping first — and note its IP (e.g. 23.215.0.39).
  • Repeat the tcpdump on ge1/ge2 for that IP — no packets are captured, because the rule only matches VLAN10 (Windows Server) as source.
Ping Adobe from OT (VLAN30).
No WAN capture for OT traffic — source 10.1.10.0/24 only is matched.
  • Pinging another SaaS app (YouTube) also yields no WAN captures — the destination doesn't match the Adobe object.
YouTube ping — not matched by the Adobe destination object.
No packets captured on the WAN interfaces for YouTube.
  • Further validate with iptables -t mangle -nvL PBR-RULES on the console — it lists the PBR-RULES chain in the mangle table with packet/byte counters.
    • -t mangle: the mangle table (marks/alters packets for PBR)
    • -L PBR-RULES: show the PBR-RULES chain · -n: numeric · -v: verbose (interface + counters)
iptables -t mangle -nvL PBR-RULES — the PBR chain with match counters.
  • The first ICMP rule shows the match: e.g. 273 packets (16380 bytes), action MARK set 0x802, protocol icmp, matching source in match-set 61 and destination in match-set 60.
Rule detail: packets/bytes matched, MARK 0x802, source match-set 61.
Destination match-set 60 — Akamai CDN ranges (e.g. 23.32.0.0–23.67.255.255) serving Adobe.

Done: PBR routes Adobe ICMP from VLAN10 direct to the WAN, scoped precisely by source + destination + port. Next, configure the Microsegmentation policy.

🧠
MENTAL NOTE
PBR overrides default routing for matching traffic. Match = Source (10.1.10.0/24) + Destination (Adobe SaaS object) + Ports (icmp:0) — all must hit. Traffic Distribution: Best picks the WAN interface by latency/loss/jitter (ge1 score 27). Validate with tcpdump -ni ge1 host <ip> (packets on ge1, none on ge2) and iptables -t mangle -nvL PBR-RULES (MARK 0x802, match-sets 60/61). Direct-to-WAN bypasses ZIA inspection — apply narrowly.
