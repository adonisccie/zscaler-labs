Lab 11: Troubleshoot WAN Failover from the Gateway

OPTIONAL LAB

In Lab 10 the Adobe ping kept running while the 8.8.8.8 ping stopped for about a minute. A helpdesk ticket describing that difference is common after an ISP outage. In this lab you use the gateway’s own tools to explain it, layer by layer: gateway health, the path each type of traffic takes, and the link and tunnel history.

Scenario: The helpdesk reports: “During the ISP outage our SaaS application kept working, but web browsing stopped for a minute.” Collect the evidence that explains why.

In this lab you will:

  • Confirm gateway health and the HA role.
  • See how the gateway chooses a path for PBR traffic and for ZIA traffic.
  • Check the link and tunnel status in the portal.

Success criteria — tick when done

  • ☐ show appliance-status returns OK on the Active unit; exactly one unit is MASTER.
  • ☐ You can point to the PBR mark (0x800, …_best table) and the ZIA mark (0x603, zia_dtls_rt table).
  • ☐ You found the ge1 Down and Up events, and zia0 and zia1 are Up.

Watch out for

  • ⚠ Command rejected — show … commands run in the Appliance Admin Console; ip … commands run in the Console tab.
  • ⚠ Different mark numbers or table names — values can differ between pods; match the lines by policy name.

💭 THINK FIRST · TROUBLESHOOT WAN FAILOVER

The helpdesk says SaaS kept working but browsing stopped for a minute. Build the explanation layer by layer.

  • Why check HA role and appliance status before anything else?
    Q1 — MODEL ANSWER
    If anything there fails, the problem is not in the policies. If the last role change predates the outage, the gap users saw was not an HA failover.
  • What do fwmark 0x800 and 0x603 tell you?
    Q2 — MODEL ANSWER
    0x800 is your PBR rule, using a table with both WAN next hops; 0x603 is the Default ZIA Rule, using the zia_dtls_rt tunnel table, which must wait for the switch to the tunnel on the other link.
  • Why can a link be Up with a poor score?
    Q3 — MODEL ANSWER
    The score is built from latency, loss and jitter; a degraded ISP can lower it while the link stays Up.
  • In the Appliance Admin Console of the Active unit, run show appliance-status.
APPLIANCE ADMIN CONSOLE — ACTIVE UNIT
$show appliance-status
EXPECTED
Gateway State ACTIVE; every WAN connectivity check returns OK; all services active; all containers Up.
In the Appliance Admin Console of the Active unit, run show appliance-status.

Why: This one command checks the gateway’s path to Zscaler, its services and its containers. If anything here fails, fix it first — the problem is not in the policies.

  • Run vyos show vrrp on both gateway tabs.
APPLIANCE ADMIN CONSOLE — BOTH GATEWAYS
$vyos show vrrp
EXPECTED
One unit is MASTER and the other BACKUP.
Last Transition on the MASTER is older than your Lab 10 test.
Run vyos show vrrp on both gateway tabs.

Why: If the last role change happened before the outage, the gateways did not swap roles, so the gap users saw was not an HA failover. That points the investigation at the WAN path.

  • In the Appliance Admin Console, run show iptables PBR-RULES -t mangle.
In the Appliance Admin Console, run show iptables PBR-RULES -t mangle.
APPLIANCE ADMIN CONSOLE — ACTIVE UNIT
$show iptables PBR-RULES -t mangle
EXPECTED
PBR-Policy: pod##-SaaS-Apps-WAN sets MARK 0x800 on Adobe ICMP.
PBR-Policy: Default ZIA Rule sets MARK 0x603.

Why: Every forwarding or routing policy becomes an iptables rule that marks matching packets. The mark records which policy the packet matched.

  • Open Troubleshooting > Console on the Active unit and run ip rule ls.
Open Troubleshooting > Console on the Active unit and run ip rule ls.
CONSOLE TAB — ACTIVE UNIT
$ip rule ls
EXPECTED
fwmark 0x800 lookup p_…_best — the routing table of your PBR rule.
fwmark 0x603 lookup zia_dtls_rt — the routing table that sends traffic into the ZIA DTLS tunnels.

Why: Each mark points to its own routing table. Adobe traffic (0x800) uses a table with both WAN next hops, so a link failure only changes the next hop. ZIA traffic (0x603) uses the tunnel table, so it has to wait for the switch to the tunnel on the other link. This is the answer to the helpdesk ticket.

  • Back in the Appliance Admin Console, run show ip route.
Back in the Appliance Admin Console, run show ip route.
APPLIANCE ADMIN CONSOLE — ACTIVE UNIT
$show ip route
EXPECTED
Two default routes: via 10.120.1.254 dev ge1 and via 10.130.1.254 dev ge2.

Why: The main table handles traffic that no policy marked. With ge1 off, only the ge2 default route remains — another way to confirm which link is in use during an outage.

  • In your site open Interfaces and select WAN. Check Link Status, Admin Status and Link Score for ge1 and ge2 on both gateways.
In your site open Interfaces and select WAN. Check Link Status, Admin Status and Link Score for ge1 and ge2 on both gateways.
In your site open Interfaces and select WAN. Check Link Status, Admin Status and Link Score for ge1 and ge2 on both gateways.

Why: The link score is calculated from latency, loss and jitter — the value that Best uses to choose a link for your PBR rule. A link can be Up and still have a poor score when the ISP is degraded.

  • Open Monitoring > WAN Health and click the WAN Score of ge1. Find the interface Down and Up events from your Lab 10 test.

Why: This history gives you the exact start and end of the outage, which you can match to the time in the helpdesk ticket.

Open Monitoring > WAN Health and click the WAN Score of ge1. Find the interface Down and Up events from your Lab 10 test.
  • Open Connectivity > Internet & SaaS. Check that zia0 and zia1 show protocol DTLS and status Up.
Open Connectivity > Internet & SaaS. Check that zia0 and zia1 show protocol DTLS and status Up.

Why: There is one DTLS tunnel per WAN link. Both must be Up again for ZIA traffic to have a backup path the next time a link fails.

Tip: Work from the outside in: gateway (show appliance-status, vyos show vrrp) → policy mark (show iptables PBR-RULES) → path (ip rule ls, show ip route) → link and tunnel (Interfaces, WAN Health, Internet & SaaS).
