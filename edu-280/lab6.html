Lab 6: Redirect and Block Domains with DNS Policies

CORE LAB

ZTB enforces DNS policy at the branch before queries leave the site, so it protects IoT and OT devices that cannot run an agent.

Scenario: You need two DNS controls: lookups of google.com from the OT segment must be answered with a fixed address, and WhatsApp must be unreachable from the IoT segment.

In this lab you will:

  • Record baseline DNS answers from OT1 and IoT.
  • Create domain objects for Google and WhatsApp.
  • Override google.com for Subnet30 and reject *.whatsapp.com for Subnet20.
  • Verify both from the endpoints.

Success criteria — tick when done

  • ☐ POD##-Google and POD##-Whatsapp objects exist.
  • ☐ google.com → 8.8.8.8 from OT1.
  • ☐ web.whatsapp.com refused from IoT.

Watch out for

  • ⚠ No change — test from the right subnet: Google on OT1 (Subnet30), WhatsApp on IoT (Subnet20).
  • ⚠ Old answer returned — flush the client cache: resolvectl flush-caches.

💭 THINK FIRST · DNS POLICIES

DNS is the first step of nearly every connection, so controlling it controls reachability.

  • Why does refusing the DNS query block WhatsApp without inspecting any traffic?
    Q1 — MODEL ANSWER
    The device never learns an IP address, so it cannot connect. This works for IoT devices that cannot run an agent.
  • Why are the two rules attached to different source subnets?
    Q2 — MODEL ANSWER
    Each rule matches only its source subnet, so the same service can be treated differently per segment — Google overridden for OT, WhatsApp blocked for IoT.
  • You still see the old answer after committing. What should you check?
    Q3 — MODEL ANSWER
    Test from the right subnet and flush the client cache with resolvectl flush-caches.
