Lab 4: Configure Content Filtering

OVERVIEW

Scenario: Labtenant's acceptable use policy blocks gambling, adult, shopping, and entertainment content on corporate devices, but users can currently reach these sites. You confirm the current behavior, create a URL Filtering rule that blocks the categories, and test the result from the user's browser.

By the end of this lab, you will be able to:

  • Confirm that a high-risk website is reachable before the policy is applied.
  • Create and activate a URL Filtering rule that blocks the Adult Materials, Shopping and Auctions, Gambling, and Entertainment/Recreation categories.
  • Test the end-user experience, and troubleshoot the rule if a site is still reachable.

Success criteria

  • ☐ 888.com loads before the rule exists.
  • ☐ Rule Risky URL Categories is at Rule Order 1, Block, Enabled, with all four categories, and the change is activated.
  • ☐ 888.com and ebay.com show a Zscaler block page that names the category.
  • ☐ You checked a streaming site and know how to look up a site's category if it isn't blocked.

Watch out for

  • ⚠ Save alone doesn't apply the rule. You must also Activate the change.
  • ⚠ The browser may show a cached page. Test in Incognito Mode.
  • ⚠ Still reachable? Check the site's URL category and that the rule status is Enabled.

💭 THINK FIRST · POLICY BY CATEGORY

You're about to block four categories with one rule. Think about why categories work, how the rule is evaluated, and what the user actually sees when it fires.

  • The rule blocks categories, not a list of sites. Why does that scale better, and what's the trade-off?
    Q1 — MODEL ANSWER
    Zscaler maintains the categorization, so a new gambling site is covered as soon as it's classified, without you editing the rule. A site list would always be out of date. The trade-off is that you depend on how a site is categorized: a site can sit in a category you didn't expect. That's why Task 4.2 tells you to look up a site's category when it's still reachable.
  • URL Filtering rules are evaluated in order, and the first match wins. Why does the lab put this rule at Rule Order 1, and what could go wrong if it were lower?
    Q2 — MODEL ANSWER
    If a higher rule matches the request first (for example, an allow rule, or the existing rule already at order 1 in the tenant), evaluation stops there and your block never applies. Rule Order 1 makes sure the block is checked first. In production you'd deliberately place narrow exceptions above broad block rules, and keep the order under review.
  • When 888.com is blocked, the user sees a page explaining which category was blocked. What role does Lab 3's SSL inspection play in making that page appear for an HTTPS site?
    Q3 — MODEL ANSWER
    The site is HTTPS, so the block page has to be delivered inside an encrypted session. Because ZIA is inspecting the traffic, it terminates the session and can answer with its own notification page, which the browser trusts. Without inspection, ZIA could still recognize the domain and stop the connection, but it couldn't show the friendly page in that session; the user would typically see a browser error instead.
Purpose: In this task, you will create a URL Filtering Policy to block risky URL categories such as gambling, adult content, shopping, and entertainment. You will also verify how content filtering controls work in ZIA to manage user access.
  • Test high-risk URL access (before configuration):
    • Open a browser on the Corp Client PC and attempt to visit a risky or unsafe website, such as 888.com (a gambling site).
    • Verify that the website is currently accessible.
    Before the rule: 888.com loads normally.
  • Create a URL Filtering policy:
    • In the Experience Center, use the Search menu to find URL Filtering and select the appropriate option (Internet Access > Policy).
    • Click Add Rule.
    URL Filtering Policy: select Add Rule. The tenant already has a rule at order 1, which is why you set your rule's order explicitly.
    • Configure the rule as follows:
    ADD URL FILTERING RULE
    FieldValue
    ActionSelect Block
    Rule NameRisky URL Categories
    Rule OrderClick Edit and change it to 1 if required
    Rule StatusEnabled
    Criteria · URL CategoriesSearch for and add:
    Adult Materials
    Shopping and Auctions
    Gambling
    Entertainment/Recreation
    Request Methods and ProtocolsEnsure all options are selected
    Add Rule: the Block action is under Actions > Web Traffic. The category box lists the selected categories and shows "+11" for the rest that don't fit.
    • Click Save and Activate.
Purpose: In this task, you'll test user access to various websites after applying the configured URL Filtering Policy.
  • Test blocked URLs:
    • Open a browser and attempt to visit a previously accessible site, such as:
      • 888.com (Gambling category)
      • ebay.com (Shopping and Auctions category)
    • Verify that these sites are now blocked based on the configured URL Filtering Policy.
    The Zscaler block page names the category: Not allowed to browse Gambling category.
  • Test streaming site access:
    • Attempt to access streaming websites such as YouTube.com or Netflix.com.
    • Verify whether these websites are blocked. If a site is still reachable, look up its URL category in ZIA; streaming sites may be classified under a category that is not included in the rule.
    In this example, YouTube is blocked and the block page names the category it matched: Video Streaming. If a streaming site still loads in your pod, look up its URL category; it may not fall under the four categories in the rule.

    Note: If testing does not work, try using Incognito Mode in the browser.

  • If the testing fails, verify the URL Filtering policy status:
    • Navigate to URL Filtering Policy and click Edit to confirm that the Rule Status is set to Enabled.

QUICK REFERENCE ▲
URL Filtering policy
Rules that allow, caution or block web access based on criteria such as URL category, user and location.
URL category
Zscaler's classification of a site (e.g., Gambling). Categories roll up into super categories and classes.
Block action
Denies the request and shows the user a Zscaler notification page.
Rule order
Rules are evaluated in ascending order and evaluation stops at the first match.
Rule Status
Enabled or Disabled. A disabled rule is skipped even if it matches.
Request methods
HTTP methods (GET, POST, CONNECT...) the rule applies to. The lab selects all of them.
URL Lookup / Site Review
Tools that show which category Zscaler assigns to a URL.
