LAB 3 · FIREWALL

Configure Firewall Filtering Policy

With traffic now tunneling to Zscaler, you enforce a default-deny firewall posture, punch a deliberate hole for ICMP and SSH, then slam the door on one specific application — WhatsApp — at the network layer where no client-side workaround can bypass it.

Lab 3: Configure Firewall Filtering Policy

OVERVIEW

Scenario: As the Zscaler administrator, you are tasked with blocking access to the external application WhatsApp to prevent organizational users from using it. At the same time, you need to ensure that SSH and ICMP traffic is enabled for all other applications. You also use the Zscaler read-only tenant to review a broader set of real-world firewall filtering rules and examine firewall logs to see how policies are evaluated and enforced in a production environment.

  • Verify the default firewall filtering policy confirms it blocks all non-web traffic.
  • Test default firewall rules that block ICMP and SSH traffic.
  • Create and configure firewall filtering rules to allow outbound ICMP and SSH traffic.
  • Create and configure firewall filtering rules to block access to specific external applications like WhatsApp.
  • Verify firewall filtering policies using practical, real-world testing scenarios.
Time: ~25 minutes
Environment: Tasks 3.1–3.3 simulated tenant · Tasks 3.4–3.5 read-only tenant

Note: This lab uses both the simulated lab environment and the Zscaler tenant. You complete Tasks 3.1–3.3 in the simulated environment (following the guided in-lab activities; the instructions below are for reference only), then switch to the Zscaler tenant for Tasks 3.4–3.5.

Task 3.1 Test Non-Web Traffic with the Default Firewall Block ▾

With Z-Tunnel 2.0, all traffic for all ports and protocols is sent to Zscaler for inspection. In this task, you generate non-web traffic from the Corp: Client PC to verify it is blocked by the default Block/Drop rule.

  1. Verify the Default Firewall Policy. From the Experience Center Portal, go to Policies > Access Control > Firewall > Firewall Filtering Policy. Confirm the Default Rule is set to Block/Drop and there are no other rules that would allow non-web traffic.
    Firewall Filtering Policy — Default Rule: Block/Drop.

    Note: Rules such as the Office 365 One Click Rule, Zscaler Proxy Traffic, and Recommended Firewall Rule explicitly allow specific traffic required for relevant features. ICMP and SSH traffic in this exercise won't match any of these rules and will fall to the Default Rule until explicitly allowed.

  2. Test the default firewall policies on the Corp: Client PC. Generate non-web traffic via ZCC — open a command prompt and run:
    ping www.google.com

    Note: This should fail with the request timing out since outbound ICMP packets are dropped by the Default Firewall rule.

  3. SSH Traffic Test — open PuTTY from the desktop, enter github.com in the Host Name field, and select Open.

    Note: This should fail. Normally the session would prompt for a username and password, but since the outbound TCP connection is dropped by the Default Firewall Rule, PuTTY displays a Fatal Error after timing out (~20 seconds).

  4. End the unsuccessful sessions — close the command prompt and exit PuTTY.

Task 3.2 Configure Firewall Policy to Allow Outbound SSH and ICMP Traffic ▾

ICMP and SSH traffic blocked in the previous task now needs to be permitted. In this task, you configure a firewall rule to allow it.

  1. Go to Policies > Access Control > Firewall > Firewall Filtering Policy and select Add Firewall Filtering Rule. Configure:
    • Rule Order: 1
    • Rule Status: Enabled (default)
    • Rule Name: allow-outbound-icmp_ssh-student-any — following the [action]-[direction]-[services]-[source-scope]-[destination-scope] naming convention
    On the Who, Where, Criteria tab, select your Student user account.
    Rule Name: allow-outbound-icmp_ssh-student-any, scoped to the Student user.
  2. Select the Services tab. Under Criteria, select the Network Services drop-down, search for and select ICMP, SSH, then select Done.
    Network Services — ICMP and SSH selected.
  3. Under the ACTION section, ensure Network Traffic is set to Allow. Select Save and activate the changes from the Activation icon (cloud with arrow) in the top-right corner.
    Action — Network Traffic: Allow, then Save + Activate.
  4. Test ICMP traffic with the new rule — on the Corp: Client PC, open a command prompt and run:
    ping www.google.com

    Note: This should now show a response since the outbound ICMP packets match the allow ICMP/SSH rule and pass through the firewall.

    Ping succeeds — ICMP now matches the new Allow rule.
  5. Test SSH traffic — open PuTTY, type github.com in Host Name, select Open.

    Note: PuTTY should now attempt a TCP connection and prompt for login, likely asking you to accept the fingerprint of the external server — indicating the SSH packets match the Allow rule and pass through the firewall.

  6. Close the sessions — close Command Prompt and exit PuTTY.

Task 3.3 Configure a Firewall Filtering Policy to Restrict Applications ▾

In this task, you review the existing Firewall Filtering Policy rules. In a real-world deployment, multiple rules are configured and evaluated top to bottom.

  1. Create a Firewall Filtering Rule from the Firewall Control menu, or Policies > Access Control > Firewall > Firewall Filtering Policy. Select Add Firewall Filtering Rule.
    Add Firewall Filtering Rule.
  2. In the Add Firewall Filtering Rule window, enter:
    • Rule Name: block_drop_all_whatspp_student_any
    • Rule Order: 2
    • Rule Status: Enabled (default)
    Under Who, Where & When, User: select the Student Admin.
    Rule Name: block_drop_all_whatspp_student_any, User: Student Admin.
  3. Under Action, set Network Traffic: Block/Drop.
    Action — Network Traffic: Block/Drop.
  4. Under the Applications tab, Network Applications: search for and select WhatsApp.
    Network Applications — WhatsApp selected.
  5. Select Done and Save to save the rule, then activate changes from the Activation icon (cloud with arrow) at the top-right.
    Save, then Activate.
    The new block rule appears in the policy list.
  6. Test the firewall rule — launch a browser and navigate to https://web.whatsapp.com.
    Access to web.whatsapp.com is restricted.

    Note: While URL Filtering Policies can also block access to web.whatsapp.com, this method may not restrict users who have the WhatsApp application installed on their system. A Firewall Filtering Policy blocks access at the network layer, ensuring complete enforcement of the access control.

Task 3.4 Review Firewall Filtering Policy ▾

In this task, you view several Firewall Filtering Policies using the Zscaler read-only tenant login. User credentials are contained in the lab access instructions provided to you via email by the instructor.

  1. In a browser, go to https://console.zscaler.com and authenticate with the read-only Zscaler tenant credentials:
    • Username: <Admin_User_ID>
    • Password: <Session_Password>
  2. Navigate to Policies > Access Control > Firewall > Firewall Control > Firewall Filtering Policy and review the rules listed.
    Read-only tenant — a fuller, production-style Firewall Filtering Policy rule set.

    Note: Rules are evaluated top to bottom — the first matching rule determines the action taken. This is important to understand when planning rule ordering in a real-world environment.

Task 3.5 Review Firewall Logs ▾

In this task, you use the Zscaler read-only tenant to examine firewall logs and understand how Firewall Filtering Policy is applied to real-world traffic.

  1. Navigate to Analytics > Firewall > Firewall Insights > Logs.
    Analytics > Firewall > Firewall Insights > Logs.
  2. In the Logs view, apply filters — for example, filter by Action, Rule Name, or Time Range to narrow down results. Select Run Query.
    Logs filter panel — Action, Rule Name, Time Range.
  3. Review the resulting log entries — observe how each entry shows the matching firewall rule, the action taken (Allow or Block/Drop), source and destination details, application, and timestamp.
    Log entries — matched rule, action, source/destination, application, timestamp.
